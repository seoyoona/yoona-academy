에이전트를 잘 짓는 사람과 못 짓는 사람의 차이는 "얼마나 복잡한 에이전트를 만드느냐"가 아니라 "얼마나 단순하게 유지하느냐"다. 프로덕션에서 안정적으로 도는 LLM 시스템 대부분은 자율 에이전트가 아니라 **잘 짜인 워크플로우**다. 복잡성은 명백히 더 나은 결과를 줄 때만 정당화되며, 그렇지 않을 때의 복잡성은 비용과 디버깅 불가능성으로 되돌아온다. 이 레슨은 가장 단순한 것부터 시작해, 필요한 만큼만 복잡해지는 패턴들을 언제·왜 쓰는지로 정리한다.

## 워크플로우 패턴: 언제, 왜

**Prompt chaining(프롬프트 연쇄).** 작업을 고정된 하위 단계로 분해해 순차 실행한다. 한 LLM의 출력이 다음의 입력이 되고, 중간에 프로그래밍 검증(게이트)을 끼울 수 있다. 언제: 작업이 깔끔하게 순차 분해되고 각 단계가 단순해질 때(예: 개요 생성 → 개요 검증 → 본문 작성). 왜: 각 호출이 쉬워져 정확도가 오른다.

**Routing(라우팅).** 입력을 분류해 전문화된 후속 경로로 보낸다. 언제: 입력이 뚜렷한 범주로 나뉘고 각 범주가 다른 처리를 요할 때(예: 환불/기술지원/일반문의 분류 후 각 전담 프롬프트로). 왜: 한 프롬프트에 모든 경우를 욱여넣을 때보다 각 경로를 최적화할 수 있다.

**Parallelization(병렬화).** 두 변형이 있다. **Sectioning**은 작업을 독립 하위 작업으로 쪼개 동시에 처리 후 합친다(예: 콘텐츠 생성과 안전성 검사를 병렬로). **Voting**은 같은 작업을 여러 번 돌려 다수결·합의를 취한다(예: 코드 취약점을 여러 번 검사해 하나라도 잡으면 플래그). 언제: 하위 작업이 독립적이거나, 다관점 투표로 신뢰도를 높여야 할 때.

**Orchestrator–workers(오케스트레이터–워커).** 중앙 오케스트레이터 LLM이 작업을 **동적으로** 하위 작업으로 분해해 워커들에게 분배하고 결과를 종합한다. Sectioning과의 차이는 하위 작업이 사전에 고정되지 않고 입력에 따라 런타임에 결정된다는 점이다. 언제: 필요한 하위 작업의 수·종류를 미리 못 정할 때(예: 여러 파일에 걸친 복합 코드 변경).

**Evaluator–optimizer(평가자–최적화자).** 한 LLM이 생성하고, 다른 LLM이 평가·피드백하며, 그 피드백으로 다시 생성하는 검증 루프다. 언제: 명확한 평가 기준이 있고 반복 개선이 측정 가능한 가치를 줄 때(예: 번역 품질, 충족되지 않은 요구사항이 있는 글쓰기).

## Worked example: Evaluator–optimizer 루프

마케팅 카피를 "톤·길이·CTA 포함" 기준으로 다듬는 검증 루프다(illustrative 의사코드/트레이스).

```python
def evaluator_optimizer(brief, max_rounds=3):
    draft = generator(brief)                  # 1) 초안 생성
    for round in range(max_rounds):
        verdict = evaluator(draft, brief)     # 2) 비평 에이전트 평가
        if verdict["status"] == "PASS":
            return draft
        draft = generator(brief, feedback=verdict["feedback"])  # 3) 피드백 반영 재생성
    return draft  # 정지 조건: 라운드 상한 도달 시 마지막 초안 반환
```

```text
round 0  generator → "지금 바로 시작하세요. 30일 무료."
         evaluator → FAIL | feedback: "CTA는 있으나 톤이 평범하고
                     타깃(시니어 엔지니어)의 언어가 아님. 길이 20% 초과."
round 1  generator(+feedback) → "운영 중인 파이프라인을 멈추지 않고
                     평가 루프를 붙이세요 — 30일, 카드 없이."
         evaluator → PASS
return → round 1 초안
```

핵심은 두 가지다. 첫째, **평가 기준이 명시적**이어야 evaluator가 일관된 판정을 낸다 — "좋게 써줘"는 루프를 발산시킨다. 둘째, **정지 조건**(`max_rounds`)이 없으면 PASS가 안 나올 때 무한 반복한다. 검증 루프의 안전장치는 항상 명시적 기준 + 라운드 상한이다.

## 진짜 자율 에이전트는 언제

위 패턴들은 대부분 워크플로우 — 경로가 사람에 의해 정해져 있다. 완전 자율 에이전트(LLM이 행동 경로를 스스로 열어가고 환경 피드백으로 자기 진로를 수정)는 **경로를 미리 못 정하고, 단계 수를 예측할 수 없으며, 환경 피드백이 필수일 때만** 정당화된다. 그리고 자율성을 허용하는 순간 세 가지가 필수가 된다: **정지 조건**(최대 스텝), **가드레일**(허용 툴·행동 제한), **비용 상한**. 이것들 없는 자율 루프는 폭주하는 청구서다.

관통하는 3원칙: **단순함**(복잡성은 측정 가능한 이득이 있을 때만), **투명성**(에이전트의 계획·행동이 드러나야 함), **잘 설계된 ACI(Agent–Computer Interface)** — 사람에게 좋은 API 문서를 쓰듯 툴 설명을 정성껏 쓰는 것. 에이전트는 툴 설명만 보고 판단하므로, 부실한 설명은 곧 헛짚는 에이전트다.

### 흔한 실패 모드와 처방

**1. 프레임워크 추상화 뒤에 로직이 숨는다.** 무슨 프롬프트가 나가고 무슨 툴이 불리는지 안 보이면 디버깅이 불가능하다. 처방: 가능하면 패턴을 직접 구성하고, 프레임워크를 쓰더라도 원시 프롬프트·툴 호출을 들여다볼 수 있게 하라.

**2. 가드레일 없는 자율 루프.** 정지·비용 상한 없는 에이전트는 토큰을 무한 소진한다. 처방: 모든 자율 루프에 max_steps·비용 상한·허용 툴 화이트리스트를 강제한다.

**3. 툴 설명 부실로 헛짚음.** 인자·반환·예시가 빈약한 툴은 모델이 오용한다. 처방: 툴 문서를 API 문서처럼 — 예시 입출력, 흔한 실수, 경계 조건까지 적어라.

## 내 시스템에 연결하기

멀티 에이전트 Slack 시스템의 라우터는 정확히 **routing 패턴**이다 — 메시지를 분류해 전문 에이전트로 보낸다. 자율 에이전트가 아니라 워크플로우이므로 단순·예측 가능하게 유지하라. 라우터 위에 오케스트레이터를 얹어 한 요청을 여러 전문 에이전트에 동적 분배하고 종합하면 **orchestrator–workers**가 된다 — 다만 분배가 정말 동적이어야(고정이면 sectioning) 정당하다. 품질이 중요한 산출물(예: 외부로 나가는 답변)에는 **evaluator–optimizer**를 붙여, 전문 에이전트의 초안을 검증 에이전트가 명시 기준으로 평가 후 통과시키되 라운드 상한을 둔다. 핸드오프 자체가 자율 루프가 되지 않도록 핸드오프 횟수 상한(정지 조건)을 가드레일로 박아라. 그리고 각 에이전트가 부르는 툴(Obsidian 검색, Blob 큐 적재 등)의 **ACI** — 설명·예시 — 를 정성껏 써야 에이전트가 헛짚지 않는다.

## ✍️ 산출물 과제

당신 시스템의 한 흐름을 골라, **어떤 패턴(prompt chaining / routing / parallelization / orchestrator–workers / evaluator–optimizer)** 으로 구현할지 한 문단으로 정확히 기술하라. 다음 용어를 명시할 것: 선택한 패턴 이름, **워크플로우 대 자율 에이전트**의 구분, **정지 조건·가드레일·비용 상한**, **ACI**. "이 작업에 자율성이 정말 필요한가, 아니면 워크플로우로 충분한가"를 먼저 판정하고, 자율을 택했다면 세 가지 안전장치를 각각 어떻게 둘지 적어라.
