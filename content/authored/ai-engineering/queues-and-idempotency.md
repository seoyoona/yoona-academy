LLM 호출은 느리고(수 초~수십 초), 비싸고(토큰 과금), 가끔 실패한다(레이트 리밋, 타임아웃, 5xx). 이 세 성질이 동시에 참이기 때문에 프로덕션 AI 시스템은 거의 항상 큐 기반 비동기 구조로 수렴한다. 그런데 큐를 도입하고도 사고가 나는 지점은 늘 같다 — 재시도가 같은 작업을 두 번 실행해 고객에게 메일이 두 번 가거나, LLM 호출이 중복 과금되거나, 독성 메시지 하나가 워커를 무한 재시작시켜 큐 전체를 멈추는 경우다. 이 레슨은 그 사고들을 구조적으로 막는 세 개념 — **전달 보장**, **idempotency**, **DLQ** — 을 정확한 메커니즘으로 다룬다.

## 큐는 무엇을 사주는가, 그리고 전달 보장의 진실

큐가 사주는 것은 세 가지다. 첫째 **부하 평탄화(load leveling)**: 순간적으로 몰리는 요청을 큐가 흡수하고 워커는 자기 처리 속도로 꺼내가므로, 트래픽 스파이크가 백엔드를 무너뜨리지 않는다. 둘째 **느린 작업 분리**: 수십 초 걸리는 LLM 호출을 요청-응답 경로 밖으로 빼내, 사용자는 즉시 "접수됨" 응답을 받고 결과는 비동기로 받는다. 셋째 **재시도·복원력**: 워커가 죽거나 호출이 실패해도 메시지가 큐에 남아 다시 처리된다.

여기서 핵심 개념이 **전달 보장(delivery guarantee)**이다.

- **at-least-once (최소 한 번)**: 메시지가 *한 번 이상* 전달됨을 보장한다. 즉 중복이 생길 수 있다. 워커가 메시지를 처리하고 ack를 보내기 직전에 죽으면, 큐는 그 메시지가 처리됐는지 알 수 없어 다시 내보낸다. 대부분의 큐 시스템의 기본값이며, 가장 흔한 운영 모델이다.
- **exactly-once (정확히 한 번)**: 정확히 한 번만 처리됨을 보장한다. 매력적으로 들리지만, 네트워크가 끊기고 노드가 죽을 수 있는 분산 환경에서 *전달* 차원의 진짜 exactly-once는 매우 어렵거나 사실상 불가능하다. 일부 시스템이 "exactly-once"를 광고하지만, 들여다보면 대개 중복 제거를 위한 추가 메커니즘을 끼운 것이다.

그래서 현실 세계의 정답은 명확하다: **at-least-once 큐 + idempotent한 처리기 = 효과적 exactly-once(effectively-once)**. 전달은 중복을 허용하되, 처리기가 중복을 무해하게 흡수하도록 설계한다. 이것이 신뢰성 있는 비동기 처리의 뼈대다.

## Idempotency: 중복을 무해하게 만드는 성질

**Idempotency(멱등성)**는 같은 연산을 여러 번 적용해도 결과가 한 번 적용한 것과 동일한 성질이다. `x = 5`는 멱등이지만 `x += 5`는 아니다. AI 워크로드에서 멱등성이 특히 절실한 이유는 중복의 대가가 크기 때문이다 — 중복 LLM 호출은 **그대로 중복 과금**되고, 외부 API 호출(결제, 캘린더 생성)은 **부작용이 두 번** 일어나며, 메시지 전송은 **고객에게 같은 알림이 두 번** 간다. at-least-once 환경에서 중복은 *예외가 아니라 정상 동작*이므로, 처리기가 멱등하지 않으면 사고는 시간문제다.

멱등성을 구현하는 표준 도구가 **idempotency key**다. 작업마다 안정적인 고유 키(예: 요청 ID, 또는 입력 내용의 해시)를 부여하고, 처리 전에 "이 키가 이미 처리됐나"를 영속 저장소에서 확인한다. 처리됐으면 다시 실행하지 않고 *저장된 이전 결과를 반환*한다. 처리 기록을 영속화하는 것이 핵심이다 — 워커가 재시작되어 메모리가 날아가도 중복을 막을 수 있어야 하기 때문이다.

> **Worked example — 멱등 처리기 의사코드 (illustrative).**
> ```python
> def handle_command(msg):
>     key = msg.idempotency_key  # 예: hash(user_id + action + payload)
>
>     # 1) 이미 처리된 키면 부작용 없이 이전 결과 반환
>     existing = store.get(key)
>     if existing is not None:
>         return existing.result        # 재실행 X → 중복 과금/전송 방지
>
>     # 2) 처음 보는 키면 실제 작업 수행 (LLM 호출 등 비싸고 부작용 있는 부분)
>     result = do_expensive_work(msg)   # call_llm(...) / send_email(...)
>
>     # 3) 키와 결과를 영속화한 뒤 ack
>     store.put(key, result)            # 워커 재시작에도 살아남음
>     return result
> ```
> 미묘한 지점: 2번과 3번 사이에서 워커가 죽으면, 작업은 됐지만 기록은 안 남아 다음 재시도가 또 실행한다 — 진짜 exactly-once가 어려운 이유가 여기 있다. 처방은 (a) `do_expensive_work` 자체를 외부 API의 idempotency key까지 전파해 멱등하게 만들거나, (b) 결과 저장과 작업을 하나의 트랜잭션/조건부 쓰기로 묶는 것이다. *완벽이 아니라 중복 창(window)을 최소화*하는 게 현실적 목표다.

## DLQ와 흔한 실패 모드

영속적으로 실패하는 메시지를 그냥 무한 재시도하면 그 한 건이 워커를 점유해 뒤의 정상 메시지를 모두 굶긴다. 이를 막는 장치가 **DLQ(dead-letter queue)**다. 메시지를 **지수 백오프(exponential backoff)**로 N회까지 재시도하고 — 매 재시도 간격을 1s, 2s, 4s…로 늘려 일시적 장애(레이트 리밋, 순간 5xx)에는 회복 기회를 주되 — 그래도 계속 실패하는 *독성 메시지(poison message)*는 메인 큐에서 빼내 별도의 DLQ로 격리한다. 효과는 둘이다: 큐 전체가 막히는 것을 방지하고, 격리된 메시지를 모아 사후 분석(왜 실패했나 — 잘못된 입력? 영구적 외부 장애?)할 수 있다.

- **실패 모드 1 — idempotency 없는 at-least-once.** 가장 흔하고 가장 비싼 사고다. 기본값이 at-least-once인데 처리기가 멱등하지 않으면 재시도·재배달이 곧 중복 과금·중복 전송으로 직결된다. *처방*: 모든 비싼/부작용 있는 커맨드에 idempotency key를 부여하고 처리 기록을 영속화한다.
- **실패 모드 2 — 백오프 없는 무한 재시도.** 실패 즉시 즉각 재시도하면 다운된 외부 서비스를 더 두드리고(thundering herd), 독성 메시지가 CPU를 태운다. *처방*: 지수 백오프 + 최대 재시도 횟수를 둔다.
- **실패 모드 3 — DLQ 부재.** 영구 실패 메시지를 격리할 곳이 없으면 그 한 건이 큐를 정지시키고, 실패를 들여다볼 데이터도 남지 않는다. *처방*: N회 초과 실패 메시지를 DLQ로 보내고 DLQ 적재 건수를 알림으로 모니터링한다.

## 내 시스템에 연결하기

이 모듈은 **Blob 커맨드 큐**에 정밀하게 매핑된다 — 커맨드를 Blob 기반 큐에 적재하고 워커가 비동기로 꺼내 처리하는 구조 자체가 at-least-once 모델이므로, 멱등성과 DLQ가 선택이 아니라 필수다.

- **idempotency key**: 각 커맨드를 적재할 때 안정적 키를 부여한다(예: `hash(채널 + 사용자 + 액션 + 페이로드)` 또는 클라이언트가 생성한 요청 ID). 워커는 LLM 호출·외부 전송 *전에* Blob 또는 별도 인덱스에서 "이 키 처리됨" 마커를 확인하고, 있으면 저장된 결과를 반환한다. 마커와 결과는 Blob에 영속화해 워커 재시작에도 중복을 막는다.
- **백오프 + DLQ**: 커맨드 처리 실패 시 재시도 횟수를 페이로드/메타데이터에 기록하며 지수 백오프로 되돌리고, N회 초과하면 별도의 *dead-letter Blob 프리픽스/큐*로 이동시킨다. DLQ 적재를 사후 분석과 알림의 입력으로 삼는다.
- **멀티 에이전트 Slack 시스템**: 라우터가 같은 사용자 메시지를 재처리하더라도 멱등 키 덕분에 전문 에이전트가 같은 작업을 두 번 실행하지 않는다 — 특히 외부로 메일·메시지를 보내는 에이전트에 필수다.
- **Obsidian 메모리 스토어**: 노트 쓰기/업데이트 커맨드도 멱등해야 같은 회고·요약이 중복 append 되지 않는다(노트 기반 RAG의 신뢰성). 키 단위 upsert로 모델링한다.

## ✍️ 산출물 과제

당신의 Blob 커맨드 큐에서 *부작용이 있는 커맨드 하나*(외부 전송 또는 과금되는 LLM 호출)를 골라, 그 커맨드가 중복 전달되었을 때 안전해지는 과정을 한 문단으로 정확히 서술하라. 그 안에서 어떤 값으로 **idempotency key**를 만들고, 처리 전 어떻게 중복을 검사하며, 영구 실패 시 **DLQ**로 어떻게 격리하는지를 명시하라. 반드시 포함할 핵심 용어: **at-least-once, exactly-once, effectively-once, idempotency(멱등성), idempotency key, 지수 백오프(exponential backoff), DLQ(dead-letter queue), poison message, 부하 평탄화(load leveling)**.
