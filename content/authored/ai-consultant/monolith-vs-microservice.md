"우리 서비스, 마이크로서비스로 만들어야 할까요?" — 이 질문을 상담에서 받는다면, 열에 아홉은 정답이 "아직 아니다"다. '마이크로서비스'가 세련되어 보여 처음부터 거기로 가려는 것은 초보의 흔한 실수다. 이 레슨은 monolith(단일 앱)와 microservice(여러 작은 서비스)의 차이, 그리고 왜 **처음엔 하나(monolith)로 시작해야 하는지**를 다룬다. 아키텍처 상담에서 가장 자주, 그리고 가장 잘못 결정되는 지점이다.

## monolith — 모든 걸 '하나의 앱'에

**monolith(모놀리스)**는 사용자 화면, API 규칙, DB 접근 등 **모든 코드를 하나의 애플리케이션으로 묶어** 돌리는 구조다. "하나의 서버 프로그램이 다 한다." 대부분의 초기 서비스는 모놀리스로 시작한다.

장점:
- **단순**: 하나의 코드베이스, 하나의 배포, 하나의 환경. 복잡도가 낮다.
- **빠른 개발**: 부품 간 호출이 그냥 함수 호출 — 네트워크를 안 타서 빠르고 디버깅 쉽다.
- **운영 단순**: 서버 한 종류, DB 한 개, 로그 한 곳.

단점:
- **커지면 무거워진다**: 코드가 거대해져 빌드·시작이 느려지고, 한 부분 변경이 전체에 영향.
- **스케일이 전체 단위**: 한 기능(예: 이미지 처리)만 트래픽 폭주해도 전체 앱을 통째로 늘려야 한다.

## microservice — 기능별로 '여러 작은 서비스'로

**microservice**는 기능(주문, 결제, 사용자 등)을 **각각 독립된 작은 서비스**로 나눠, 서로 네트워크(API)로 통신하는 구조다. 각 서비스가 자기 DB를 갖고, 따로 배포된다.

장점:
- **독립 스케일**: 결제 서비스만 트래픽 폭주하면 결제 서비스만 늘린다.
- **독립 배포**: 한 팀이 결제 서비스만 바꿔 따로 배포 — 전체에 영향 적음.
- **팀 분업**: 서비스별로 팀이 나뉘어 소유권 명확.

단점 — **초기엔 치명적**:
- **복잡도 폭발**: 여러 서비스, 여러 DB, 여러 배포, 서비스 간 통신(API) 설계, 장애 추적(분산 로그) — 운영 부담이 기하급수.
- **네트워크 비용/지연**: 함수 호출이 아니라 HTTP/gRPC 호출이라 느리고, 실패·재시도 처리가 붙는다.
- **데이터 일관성 어려움**: 여러 DB에 걸친 트랜잭션이 복잡(Phase 3 트랜잭션의 확장판).
- **인프라 요구**: 서비스 discovery, API gateway, 분산 추적, 컨테이너 오케스트레이션 등 대단위 장비·지식 필요.

## 왜 '처음엔 하나로'인가 — 결정적 이유

초기 서비스는 트래픽도 적고, 팀도 작고, 요구사항도 자주 바뀐다. 이 단계에서 마이크로서비스를 고르면:

- **복잡도가 제품보다 먼저 커진다.** 인프라와 통신 설계에 시간을 다 쓰고 기능은 못 만든다.
- **요구사항 변화에 취약**: 서비스 경계를 잘못 나누면, 바뀔 때마다 서비스를 쪼개고 합쳐야 한다 — 모놀리스에선 그냥 파일 옮기면 끝날 일이.
- **"스케일" 문제가 아직 안 왔다**: 초기엔 모놀리스 한 벌로 충분히 감당 가능하다.

**마이크로서비스는 '스케일·조직 크기' 문제를 푸는 도구지, '멋져 보여서' 쓰는 게 아니다.** 그 문제가 실제로 왔을 때(트래픽 폭주, 팀 10명 이상, 배포 충돌 잦음) 그때 가야 한다.

## 점진적 분리 — '모놀리스 → 부분 분리'

"처음엔 하나"가 "영원히 하나"는 아니다. 모놀리스 안에서도 **모듈을 깔끔하게 나눠 두면**, 나중에 특정 모듈만 떼어 서비스로 독립시키기 쉽다. 이를 '모놀리스 내부의 모듈화'라 부른다 — 코드는 하나지만, 주문/결제/사용자 부분이 폴더로 깔끔히 나뉘어 있어 나중에 떼어내기 좋은 상태.

이게 시니어의 설계 감각이다: **지금은 하나(monolith)로 가되, 미래에 잘게 떼어낼 수 있도록 경계(modular)를 깔끔히 유지.** "영원히 뭉텅이"도 아니고 "처음부터 산산조각"도 아닌, 중간의 균형.

## worked example: "이커머스" 아키텍처 상담

고객: "쇼핑몰 만들 건데, 상품·주문·결제·배송 각각 마이크로서비스로요."

시니어 답변:
1. **초기엔 모놀리스로** — 상품·주문·결제·배송이 한 앱 안의 **모듈**(폴더)로. 하나의 DB에 각 표(product, order, payment, shipment). 배포 한 번, 환경 한 벌.
2. **모듈 경계를 깔끔히** — 주문 모듈이 결제 모듈을 '함수 호출'로 쓰되, 경계를 문서화. 나중에 떼어내기 좋게.
3. **스케일 신호가 오면 그때 분리** — 예: 결제 트래픽이 폭주해 결제만 따로 늘려야 할 때, 결제 모듈을 별도 서비스로 독립.
4. **DB도 점진 분리** — 처음엔 한 DB의 여러 스키마, 결제 독립 시 결제 스키마만 별도 DB로.

"마이크로서비스로요"라는 고객 요구를 "지금은 모놀리스+모듈화, 필요해지면 그때 분리"로 되돌리는 것이 상담 가치다. 복잡도를 미리 끌어오지 않는 판단.

## 흔한 실패 모드와 처방

- **처음부터 마이크로서비스.** 복잡도가 제품보다 먼저 커져 MVP 실패. 처방: 초기엔 모놀리스(모듈화)로.
- **모놀리스를 '뭉텅이'로 키운다.** 경계 없이 뒤엉켜 나중에 못 뗌. 처방: 모듈 단위로 깔끔히 나눠 유지.
- **잘못된 경계로 서비스를 나눈다.** 자주 같이 바뀌는 것을 분리하면 통신 비용만. 처방: 분리는 '독립적으로 스케일/배포되어야 할 때'로 제한.
- **DB를 처음부터 분산.** 트랜잭션·일관성 지옥. 처방: DB는 한 곳에서, 서비스만 분리(그것도 필요시).

## 상담에 바로 쓰는 한 줄

"마이크로서비스요?"라는 질문엔, "지금 규모에선 모놀리스(모듈화)가 맞다 — 스케일·팀이 커지면 그때 분리"로 답하라. 복잡도를 미리 부르지 않는 것이 상담력이다.

## 개발자가 이 단어 말할 때

- **monolith / 모놀리스** — 하나의 앱으로 다 처리하는 구조.
- **microservice / 마이크로서비스** — 기능별 작은 서비스로 나눈 구조.
- **모듈화(modular monolith)** — 하나의 앱 안에서 경계를 깔끔히 나눈 상태(이관 대비).
- **서비스 경계(boundary)** — 무엇을 분리할 것인가의 기준.
- **API gateway / 서비스 디스커버리** — 마이크로서비스 운영 인프라(초기엔 불필요).
- **분산 트랜잭션 / eventual consistency** — 여러 서비스에 걸친 데이터 일관성 문제.

## ✍️ 산출물 과제

본인 서비스를 모놀리스로 설계하되, 내부를 모듈(폴더)로 나눠 보라. "어떤 모듈이 트래픽/팀 규모가 커지면 가장 먼저 분리 후보인가"를 하나 고르고, 그 이유(독립 스케일/배포 근거)를 적어라.

## 한 걸음 더

"마이크로서비스"의 매력에 속지 말 것 — 그 복잡도는 소규모 팀엔 치명적이다. 대부분의 성공적 서비스는 "잘 모듈화된 모놀리스"로 시작해, 진짜 필요해질 때만 한 조각씩 분리했다. 아키텍처는 패션이 아니라 문제에 대한 응답이어야 한다.
