라우터에 temperature를 0.9로 박아두면, 같은 메시지를 두 번 보냈을 때 한 번은 `billing` 에이전트로, 한 번은 `support` 에이전트로 흩어진다. 라우팅은 분류 문제이고 분류에는 단 하나의 정답 분포가 있는데, 우리가 모델의 출력 분포를 일부러 평탄하게 만들어 놓았기 때문이다. 모델이 텍스트를 만드는 과정 — 자기회귀 생성과 그 위에 얹는 샘플링 제어 — 을 정확한 메커니즘으로 이해하지 못하면, 어디에 결정성을 박고 어디에 다양성을 풀지를 감으로 정하게 되고, 그 감은 프로덕션에서 흔들리는 라우터, 중간이 비는 긴 컨텍스트, 끝없이 반복되는 출력으로 되돌아온다.

## 자기회귀 생성과 logits, 그리고 temperature

언어 모델은 한 번에 문장을 뱉지 않는다. 매 스텝마다 "지금까지의 토큰열이 주어졌을 때 다음 토큰의 확률분포" P(다음 | 지금까지)를 계산하고, 그 분포에서 토큰 하나를 골라 뒤에 이어 붙인 뒤, 늘어난 토큰열을 다시 입력으로 넣어 같은 일을 반복한다. 이것이 autoregressive(자기회귀) 생성이다. 모델의 마지막 층은 어휘 사전 크기만큼의 실수 벡터 — logits — 를 내고, 여기에 softmax를 씌워 확률로 바꾼다.

핵심은 softmax 직전에 logits를 temperature T로 나눈다는 점이다: `P_i = softmax(logits_i / T)`. T가 1이면 모델 원래 분포, T가 작아지면 큰 logit과 작은 logit의 격차가 벌어져 분포가 뾰족해지고(결정적), T가 커지면 격차가 줄어 분포가 평탄해진다(다양). 구체적으로 보자. "대한민국의 ___" 다음 토큰에 대해 모델이 다음 분포를 냈다고 하자(illustrative).

| 토큰 | P (T=1.0) |
|------|-----------|
| 수도 | 0.82 |
| 도시 | 0.07 |
| 땅   | 0.05 |
| 국기 | 0.04 |
| 인구 | 0.02 |

이 확률은 logits를 거꾸로 추정하면 대략 `수도=2.0, 도시=-0.46, 땅=-0.80, 국기=-1.02, 인구=-1.71` 수준이다(상수항 무시). 여기에 T를 바꿔 다시 softmax를 돌리면:

- **T=0.5** (logits를 2배로): 수도≈0.965, 도시≈0.012, 나머지는 거의 0. 분포가 "수도"로 쏠린다.
- **T=2.0** (logits를 절반으로): 수도≈0.52, 도시≈0.16, 땅≈0.14, 국기≈0.12, 인구≈0.06. 1위와 2위의 격차가 좁아져 "도시"나 "땅"이 뽑힐 여지가 생긴다.

T는 순위를 바꾸지 않는다 — 항상 "수도"가 1등이다. 다만 2등 이하가 뽑힐 **확률의 폭**을 키우거나 줄일 뿐이다. 그래서 T를 올린다는 것은 "가끔 일부러 1등이 아닌 걸 고른다"는 뜻이고, 이게 창의성의 정체이자 사실 오류의 원천이다.

## top-k, top-p, 그리고 greedy의 함정

temperature가 분포의 모양을 바꾼다면, top-k와 top-p는 **후보 집합 자체를 자른다**. top-k는 확률 상위 k개만 남기고 나머지를 0으로 만든 뒤 재정규화한다. 위 예에서 k=2면 후보는 {수도, 도시}뿐이고, 0.82:0.07을 0.92:0.08로 다시 normalize해서 그 둘 중에서만 샘플링한다.

top-p(nucleus sampling)는 개수가 아니라 **누적 확률**로 자른다. p=0.9면 확률 높은 순으로 더해가다 누적합이 0.9를 넘는 순간까지만 후보로 남긴다. 위 분포에서 0.82(수도)+0.07(도시)=0.89, 여기에 0.05(땅)를 더하면 0.94이므로 컷오프는 {수도, 도시, 땅}이다. top-p의 장점은 분포가 뾰족할 땐 후보를 1~2개로 좁히고(확신이 강하면 보수적으로), 분포가 평탄할 땐 후보를 많이 남겨(애매하면 다양하게) **상황에 적응**한다는 점이다. top-k는 분포 모양과 무관하게 항상 k개라 이 적응성이 없다.

반대 극단이 greedy decoding(T→0, 항상 argmax)이다. greedy는 결정적이라 좋아 보이지만 반복 루프에 잘 빠진다. 메커니즘은 이렇다: 모델이 "감사합니다. 감사합니다."를 한 번 생성하면, 그 반복된 컨텍스트가 다음 "감사합니다"의 logit을 더 끌어올린다 — 모델은 자기가 쓴 패턴을 강한 증거로 받아들이기 때문이다. argmax는 이 상승한 logit을 무조건 선택하므로 한 번 진입한 루프를 빠져나올 확률적 탈출구가 없다. 약간의 T나 repetition penalty가 이 루프를 깨는 이유가 여기 있다.

```python
import numpy as np
def sample(logits, T=1.0, top_p=1.0):
    logits = np.array(logits) / T
    p = np.exp(logits - logits.max()); p /= p.sum()
    idx = np.argsort(p)[::-1]
    cum = np.cumsum(p[idx])
    keep = idx[:np.searchsorted(cum, top_p) + 1]   # nucleus
    q = p[keep] / p[keep].sum()
    return np.random.choice(keep, p=q)
```

## 컨텍스트 윈도우와 lost in the middle

생성된 토큰열은 매 스텝 다시 입력으로 들어가므로, 비용과 지연은 처리하는 토큰 수에 거의 비례한다(어텐션은 입력 길이에 대해 더 가파르게 든다). 그래서 컨텍스트 윈도우는 단순한 "최대 길이" 제한이 아니라 **예산**이다. prefill(입력 전체를 한 번에 인코딩하는 단계)과 decode(토큰을 하나씩 뽑는 단계)는 비용 구조가 다른데 — prefill은 병렬, decode는 순차 — 긴 입력은 prefill을, 긴 출력은 decode를 키운다.

더 미묘한 문제가 lost in the middle이다. 긴 입력에서 정작 필요한 정보가 **중간**에 있으면 모델의 성능이 떨어지고, 같은 정보가 맨 앞이나 맨 뒤에 있으면 잘 쓴다. 어텐션이 시퀀스의 양 끝(특히 시작과 직전 토큰)에 더 강하게 걸리는 경향과, 학습 데이터에서 핵심이 보통 앞뒤에 배치된다는 편향이 겹친 결과다. 처방은 단순하다: 가장 중요한 지시·문서는 컨텍스트의 **맨 앞이나 맨 뒤**에 두고, 덜 중요한 보조 자료를 가운데에 채운다. RAG에서 검색된 청크를 관련도 순으로 정렬할 때, 1등을 한가운데가 아니라 양 끝에 배치하는 재배열(reordering)이 효과를 내는 이유다.

## 트레이드오프와 실패 모드

의사결정 기준은 한 문장으로 압축된다: **정답이 하나면 T를 낮추고, 정답이 여럿이면 T를 올린다.** 분류, 라우팅, 추출, JSON·함수 호출 같은 structured output은 T=0~0.3으로 결정성에 가깝게 둔다. 브레인스토밍, 카피 변주, 다양한 예시 생성처럼 "여러 좋은 답"이 있는 작업만 T=0.7~1.0으로 푼다.

흔히 저지르는 실패는 세 가지다. 첫째, **라우터에 높은 T**를 두는 것 — 분류는 단일 정답 문제인데 분포를 평탄하게 만들어 같은 입력이 다른 에이전트로 흩어진다. 처방: 라우팅·분류 호출은 T=0, 가능하면 structured output으로 강제. 둘째, **T와 top-p 동시 과상향** — T로 분포를 평탄하게 만든 뒤 top-p까지 1.0 가까이 열면 꼬리의 저확률 토큰까지 들어와 사실 오류가 급증한다. 둘 중 **하나만** 다양성 손잡이로 쓰고 나머지는 보수적으로 고정한다. 셋째, **핵심 지시를 긴 컨텍스트 한가운데 매장**하는 것 — "반드시 JSON으로만 답하라" 같은 제약을 10K 토큰짜리 자료 중간에 끼워 넣으면 모델이 흘려버린다. 시스템 지시는 맨 앞, 출력 형식 재확인은 맨 뒤에 둔다.

## 내 시스템에 연결하기

**멀티 에이전트 Slack 시스템**의 라우터는 "이 메시지를 어느 전문 에이전트로 보낼까"를 분류하는 단일 정답 작업이다. 따라서 라우터 LLM 호출은 T=0, 출력은 `{"agent": "..."}` 형태의 structured output으로 못 박아 분포가 흔들릴 여지를 없앤다. 반대로 전문 에이전트가 사용자에게 최종 답변 문장을 작성하는 단계는 약간의 T(예: 0.5~0.7)를 허용해 자연스러움을 준다 — 같은 손잡이를 단계별로 다르게 잡는 것이 핵심이다. 핸드오프 시 누적되는 대화 이력은 컨텍스트 예산을 갉아먹으므로, 직전 핸드오프의 결론을 요약해 맨 앞에 두고 원본 이력은 뒤로 미뤄 lost in the middle을 피한다.

**Obsidian 메모리 스토어** 기반 RAG에서는 검색된 노트 청크의 배치가 곧 성능이다. 관련도 1·2등 청크를 컨텍스트의 맨 앞과 맨 뒤에 배치하고, 답변 생성은 사실 충실이 중요하므로 T를 낮게(0.2~0.3) 둔다.

**Blob 커맨드 큐**의 워커가 커맨드를 파싱·분류하는 LLM 단계 역시 단일 정답 작업이므로 T=0이 기본이다. 재시도 시 같은 커맨드가 다른 결과로 분류되면 멱등성이 깨지므로, 결정성은 선택이 아니라 요구사항이다.

## ✍️ 산출물 과제

당신 시스템의 LLM 호출 한 곳을 골라, 그 호출이 왜 그 temperature 값을 써야 하는지를 정확한 용어로 한 문단 설명하라. 반드시 다음 용어를 사용할 것: **autoregressive(자기회귀)**, **logits**, **softmax(logits/T)**, **top-p(nucleus)**, **greedy decoding**, **lost in the middle**. "단일 정답 작업인가, 여러 정답 작업인가"라는 판단과 T·top-p 중 어느 손잡이를 잡고 어느 것을 고정했는지를 명시하라.
