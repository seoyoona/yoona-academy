"서비스가 느려졌어요." — 이 말이 나오면 원인은 보통 둘 중 하나다: 데이터가 많아져 조회가 느려졌거나(→ 인덱스), 같은 데이터를 반복 조회해서 서버가 헥헥대거나(→ 캐시). 이 레슨은 "느려지기 시작할 때" 쓰는 세 가지 레버 — 인덱스, 캐시, 수평 확장 — 를 다룬다. 초기엔 필요 없지만, 트래픽/데이터가 쌓이면 반드시 부닥치는 단계다. PM이 어느 레버를 언제 당길지 아는 것이 성능 상담의 뼈대다.

## 먼저 원인을 가린다 — 어디서 느린가

"느리다"는 원인이 어디냐에 따라 처방이 다르다:

- **DB 조회가 느리다**: 특정 쿼리가 오래 걸린다 → **인덱스** 의심.
- **같은 데이터를 자꾸 다시 계산/조회한다**: 반복 작업 → **캐시** 의심.
- **트래픽이 늘어 서버가 한계**: CPU/메모리 포화 → **확장(scale)** 필요.
- **프론트/네트워크**: 화면 자체·이미지 크기·대역폭 → 별개 최적화.

이 레슨은 앞 세 가지(DB·캐시·확장)를 다룬다. 핵심은 **"원인이 뭔지 먼저 재고(측정)하고, 그 원인에 맞는 레버를 당긴다"** — 찍어서 고치지 않는다.

## 인덱스 — DB 조회를 빠르게

**인덱스(index)**는 Phase 3에서 본 '색인'이다. 자주 검색하는 열에 두면, 전체 훑기(full scan) 대신 해당 행으로 바로 뛰어간다 — 책의 찾아보기처럼.

"느려졌다"의 첫 번째 원인이 자주 여기에 있다:
- 데이터가 수만~수백만 행이 되면, 인덱스 없는 `WHERE` 조회가 처음부터 끝까지 훑어 느려진다.
- 자주 검색하는 열(예: `reservations.date`, `users.email`)에 인덱스를 추가하면 극적으로 빨라진다.

처방 순서: (1) 느린 쿼리를 찾아 (실행 계획/로그) (2) 그 쿼리의 WHERE/JOIN 조건 열에 인덱스가 있나 확인 (3) 없으면 추가. **비용**: 인덱스는 쓰기(INSERT)를 약간 느리게 하고 용량을 쓴다 — 남발은 금물, "자주 검색하는 열"에만.

## 캐시 — 같은 결과를 빠르게

**캐시(cache)**는 자주 쓰는 결과를 임시로 저장해두고, 다음엔 DB까지 안 가고 그걸 바로 돌려주는 것이다.

예:
- "인기 상품 목록"은 잘 안 바뀐다 → DB에서 매번 조회 대신, 캐시(Redis 등)에 5분치 저장 → 조회 수십 배 빨라짐.
- 사용자 프로필도 캐시하면 DB 부하가 줄어든다.

"느려졌다"의 두 번째 원인: **같은 데이터를 반복 조회**하느라 DB가 헥헥댈 때. 캐시가 DB 부하를 크게 줄인다.

처방 순서: (1) 반복 조회가 많은 데이터(잘 안 바뀌는 목록/집계) 찾기 (2) 캐시(Redis·메모리)에 짧은 시간 저장 (3) 원본이 바뀌면 캐시도 갱신(무효화). **주의**: 캐시된 데이터가 "낡은(stale)" 것이 될 수 있으니, "얼마나 오래 낡은 데이터를 허용할까"를 정해야 한다 — 실시간성이 중요하면 캐시 주기를 짧게.

## 확장(scale) — 서버를 늘린다

트래픽이 늘어 서버 한 대가 한계일 때, 두 가지로 늘린다:

- **수직 확장(scale up)**: 서버 한 대를 더 좋게(CPU/메모리 업). 단순하지만 한계가 있고 비싸진다.
- **수평 확장(scale out)**: 서버를 여러 대로 늘려 로드밸런서가 트래픽을 분산. 이론상 계속 늘릴 수 있지만, **서버 간 상태 공유**(세션·파일) 처리가 필요 — '무상태(stateless)' 설계가 전제돼야 잘 된다.

"느려졌다"의 세 번째 원인: 서버 자체가 포화. 이때 확장. 단, **DB는 확장이 어렵다**(관계형 DB 수평확장은 복잡) — 그래서 먼저 인덱스·캐시로 DB 부하를 줄이고, 앱 서버를 수평 확장하는 순서가 흔하다.

## 세 레버의 순서 — 인덱스 → 캐시 → 확장

보통 이 순서로 당긴다 (비용/효과 면에서):

1. **인덱스**: 제일 싸고 효과 큼. 느린 쿼리 열에 추가. (거의 항상 먼저.)
2. **캐시**: DB 부하를 줄임. 반복 조회가 많을 때.
3. **확장**: 인덱스·캐시로도 안 될 때, 서버/인프라를 늘림. (가장 비싸고 복잡.)

이 순서를 모르면 "느리니까 서버를 늘리자"(비싼 확장)부터 하는 실수를 한다 — 실제론 인덱스 하나면 해결될 걸. **가장 싼 레버부터 당기는 것**이 성능 엔지니어링의 기본이다.

## worked example: "예약 화면이 느려졌어요" 번역

증상: 예약 목록 화면 로딩이 3초로 느려짐. 원인 탐색:
1. **측정**: 예약 목록 쿼리가 2.5초 걸림 → DB 조회 병목.
2. **인덱스 점검**: `reservations`를 `WHERE date = ?`로 거르는데 `date`에 인덱스가 없음 → **`date` 인덱스 추가** → 쿼리 0.1초로. (싸고 결정적.)
3. **캐시 검토**: "오늘 예약 가능 시간"이 잘 안 바뀌어 반복 조회 → 캐시 1분 도입 → DB 부하 추가 감소.
4. **확장**: 아직 서버 CPU 30%라 확장 불필요. 인덱스+캐시로 충분.

"느려졌어요"가 (1) 측정 (2) 인덱스 (3) 캐시 (4) 확장 순의 레버로 번역. **확장(비싼 것)을 먼저 꺼내지 않고, 인덱스(싼 것)로 끝낸 것**이 핵심. 이 흐름을 상담에 가져가면 "무조건 서버 업그레이드"를 피할 수 있다.

## 흔한 실패 모드와 처방

- **측정 없이 찍어서 고친다.** 인덱스도 아닌데 인덱스 추가. 처방: 먼저 어디서 느린지 측정(쿼리 로그/실행계획/모니터링).
- **확장(scale)부터 한다.** 비싸고 근본 해결이 아닐 수 있음. 처방: 싼 레버(인덱스·캐시)부터.
- **캐시 무효화를 안 한다.** 낡은 데이터가 보임. 처방: 원본 변경 시 캐시 갱신/만료 설계.
- **수평 확장 전에 무상태화 안 함.** 세션·파일이 한 서버에 묶여 늘려도 안 됨. 처방: 확장 전 상태를 외부(공유 저장소)로 빼기.

## 상담에 바로 쓰는 한 줄

"느려요"를 받으면, "먼저 어디서 느린지 측정하고, 싼 것부터(인덱스 → 캐시 → 확장) 당긴다"고 답하라. 무조건 '서버 업그레이드'는 최후의 수단이다.

## 개발자가 이 단어 말할 때

- **인덱스 / 실행 계획(explain)** — 색인 / 쿼리가 어떻게 도는지 보는 도구.
- **풀 스캔** — 표 전체 훑기(인덱스 없으면 느림).
- **캐시 / Redis / 무효화(invalidation)** — 임시 저장 / 대표 도구 / 낡은 캐시 지우기.
- **scale up / scale out** — 한 대를 키움 / 여러 대로 늘림.
- **무상태(stateless) / 로드밸런서** — 서버가 상태를 안 가짐 / 트래픽 분산기.
- **병목(bottleneck)** — 전체 속도를 깎는 가장 느린 지점.

## ✍️ 산출물 과제

본인 서비스의 "느려질 만한 화면/쿼리" 하나를 고르고, 느려졌을 때 당길 레버를 (1) 측정 (2) 인덱스 (3) 캐시 (4) 확장 순으로 적어라. 각 단계에서 "무엇을 하겠는가"를 한 줄씩 적고, 왜 가장 싼 레버부터인지 이유를 적어라.
