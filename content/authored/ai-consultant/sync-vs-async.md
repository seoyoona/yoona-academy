고객이 "엑셀 올리면 사용자 1천 명한테 알림 보내 주세요"라고 할 때, "엑셀 올리기 → 파싱 → 발송"이 한 번에 끝날 거라 생각하면 안 된다. 한 번에(동기) 처리하면 사용자는 발송 끝날 때까지 30초를 기다리며 하얀 화면을 본다. 정답은 "요청은 즉시 받고, 무거운 일은 뒤로 미뤄서(비동기) 처리"다. 이 레슨은 동기 vs 비동기, 그리고 큐·배치·웹훹이 어떤 역할을 하는지 다룬다. **고객 요구 → 처리 구조 번역**의 핵심 레슨이다.

## 동기(synchronous) — '요청→결과'를 바로 기다린다

**동기** 처리는 "요청하면, 끝날 때까지 기다렸다가 결과를 받는" 방식이다. 브라우저가 서버에 요청 → 서버가 다 끝낼 때까지 → 응답. 일상적 대부분(로그인, 게시글 조회, 저장)이 동기다.

특징:
- **단순·직관**: 순서대로, 결과를 바로 안다.
- **짧은 작업에 적합**: 수백 ms 안에 끝나는 일엔 이게 최적.
- **무거운 작업엔 부적합**: 오래 걸리면 사용자가 기다리고, timeout으로 끊긴다.

## 비동기(asynchronous) — '요청'과 '처리'를 분리

**비동기** 처리는 "요청은 즉시 접수하고, 실제 처리는 뒤에서(나중에) 한다"는 방식이다. 사용자는 "접수됨"을 바로 받고, 무거운 일은 백그라운드에서 돌아간 뒤 나중에 알려준다.

핵심 도구 세 가지:

- **큐(queue)**: "할 일"을 줄 세워 두고, 워커가 하나씩 꺼내 처리. 엑셀 발송·이미지 변환 같은 무거운/오래 걸리는 일을 즉시 처리 대신 큐에 넣는다.
- **배치(batch)/스케줄러**: 정해진 시간(매일 새벽, 매 5분)에 돌아가는 작업. "예약 1시간 전 알림"처럼 시간 기반 트리거.
- **웹훹(webhook)**: 외부 서비스가 "끝났어/상태 바뀌었어"라고 우리에게 알려주는 역방향 호출(Phase 2 참고). 결제 완료 알림·전송 결과 회신.

## 언제 동기, 언제 비동기?

**동기로 충분할 때:**
- 빠르게 끝나는 작업(수백 ms 이내): 조회, 저장, 로그인.
- 결과를 즉시 봐야 하는 작업: "저장했습니다" 확인.

**비동기로 가야 할 때:**
- **오래 걸리는 작업**: 대량 이메일/푸시 발송, 엑셀 파싱, 이미지·영상 변환, 리포트 생성.
- **외부 대기**: 결제사 응답, 외부 API 호출이 느릴 때.
- **시간 기반**: "예약 1시간 전 알림", "매일 리포트" — 스케줄러/배치.
- **신뢰성**: 실패 시 재시도가 필요한 작업 — 큐에 넣고 재시도.

판별 질문: **"이 작업이 1초 안에 끝나는가? 아니면 사용자가 기다리면 안 되는가?"** 후자면 비동기.

## worked example: "엑셀 업로드 → 1천명 알림" 번역

고객 요구: "관리자가 엑셀 올리면 조건 맞는 사용자 1천명에게 알림."

틀린(동기) 구현:
```
업로드 → 즉시 1천명 파싱+조회+발송 (30초~수분) → 응답
→ 사용자는 30초 하얀 화면, timeout으로 실패, 재시도 불가
```

맞는(비동기) 구현:
1. **업로드**: 엑셀 파일을 S3에 올리고, "발송 배치" 행을 DB에 만듦(status="대기"). **즉시 "처리 중입니다" 응답** — 사용자는 안 기다림.
2. **큐**: 서버가 "이 배치 작업해라"를 **큐**에 넣음.
3. **워커**: 백그라운드 워커가 큐에서 꺼내 — 엑셀 파싱 → 대상 1천명 조회 → 발송(FCM/이메일)을 진행. 실패 건은 재시도.
4. **웹훹/상태**: 발송 서비스가 "997건 성공/3건 실패" 회신(웹훹) → DB의 배치 status를 "완료(실패3)"로 갱신.
5. **완료 알림**: 관리자 화면에 "발송 완료, 실패 3건 — 재발송 버튼" 표시(폴링 또는 실시간).

이렇게 하면 사용자는 즉시 응답받고, 무거운 일은 안정적으로(재시도·로그 포함) 돈다. **"간단한 알림"이 큐+워커+웹훹+상태머신의 복합 구조로 번역되는 것** — 이 번역이 PM 상담력의 핵심이다. (Phase 2 백엔드 단어장과 연결되는 결정적 예시.)

## "왜 지금 안 되고 나중에?" — 사용자 경험 설계

비동기를 쓰면 사용자에게 "지금 당장 안 됨"을 설명해야 한다. 그래서 **상태 표시 UI**가 동반돼야:

- "처리 중…" (스피너/진행률)
- "완료" / "실패 N건" (결과 알림)
- 실패 시 "재시도" 버튼

"즉시 안 됨"을 사용자에게 어떻게 보여줄지까지 기획하는 것이 비동기 기능의 전부다. 동기(즉시 결과)와 비동기(나중에, 상태 표시)는 UX 설계부터 다르다.

## 실 사례(익명화) — 대량 발송을 "즉시 응답 + 큐"로 바꾼 사례

> 실제 프로젝트 패턴을 익명화해 온다.

한 서비스에서 "엑셀을 올리면 수천 건을 처리·발송"하는 기능이 있었다. 처음엔 **동기**로 짜서 — 사용자가 올리면 끝날 때까지 화면이 멈춰 있었다(수십 초~실패). 이걸 **비동기**로 바꿨다: 올리면 즉시 "처리 중" 응답, 실제 작업은 **큐→워커**로 뒤에서, 완료·실패는 상태로 표시. 사용자는 안 기다리고, 실패 건은 재시도까지 가능해졌다.

교훈: "오래 걸리는 작업(발송·변환·리포트·대량 처리)"을 만나면 **"즉시 응답 + 큐(비동기) 처리 + 상태 표시"** 구조가 정답이다. 단, 비동기는 디버깅이 어려워지니 **상태 추적(진행/완료/실패·로그)**이 함께 와야 한다 — 없으면 "가끔 안 된다"는 지옥이 생긴다.

## 흔한 실패 모드와 처방

- **무거운 작업을 동기로.** 사용자 대기·timeout·실패. 처방: 1초 이상 걸리면 큐로 비동기.
- **상태 표시를 안 한다.** "처리됐나?"를 사용자가 모름 → 문의 폭주. 처방: 진행/완료/실패 상태 UI 동반.
- **재시도를 안 건다.** 일시적 실패가 영구 실패가 됨. 처방: 큐 작업은 재시도 정책(횟수/간격) 포함.
- **큐를 쓰는데 "순서 보장"을 안 한다.** 순서가 중요한 작업이 꼬임. 처방: 순서 보장이 필요하면 큐 설계에 반영(FIFO).

## 상담에 바로 쓰는 한 줄

요구가 "오래 걸리는 작업/대량 처리/시간 기반"이면, "즉시 응답 + 큐(비동기) 처리 + 상태 표시" 구조를 제안하라. 이 세 단어가 비동기 설계의 전부다.

## 개발자가 이 단어 말할 때

- **동기 / 비동기(sync/async)** — 요청과 처리를 한꺼번에 / 분리.
- **큐 / 워커** — 할 일 줄 / 꺼내서 처리하는 일꾼.
- **배치 / 크론(cron)** — 정기적으로 도는 작업 / 시간 스케줄러.
- **웹훹(webhook)** — 외부→우리로 오는 상태 알림.
- **폴링 / 롱폴링 / 실시간(WebSocket)** — 클라이언트가 주기적 물어보기 / 서버가 밀어주기.
- **재시도(retry) / idempotent** — 실패 시 다시 / 여러 번 와도 한 번 효과(중복 방지).

## ✍️ 산출물 과제

본인 서비스의 "무거운/오래 걸리는 작업" 하나를 고르고, 그것을 (1) 즉시 응답 (2) 큐/배치 처리 (3) 상태 표시(진행/완료/실패) (4) 실패 시 재시도 의 네 단계로 기획하라. 각 단계를 한 줄로 적어라.

## 한 걸음 더 — 비동기의 대가: '디버깅이 어렵다'

비동기는 빠른 응답과 안정성을 주지만, 한 가지 분명한 대가가 있다 — **문제가 생겼을 때 원인을 찾기 어렵다.** 동기 코드는 "이 줄에서 실패"가 한눈에 보이지만, 큐에 넣은 작업이 백그라운드 워커에서 실패하면 사용자는 "안 됐다"만 느끼고 서버 로그를 뒤져야 원인이 보인다. 그래서 비동기를 도입하면 반드시 **관측 가능성(observability)**이 따라온다: 각 작업에 id를 붙여 상태(대기/진행/성공/실패)를 DB에 남기고, 실패 원인을 로그로 저장하고, 오래 멈춘 작업을 알림으로 잡는다. "큐 도입"과 "큐 상태 추적"은 한 세트다. 추적 없는 비동기는 "가끔 안 된다는데 왜인지 모름"이라는 지옥을 만든다. 상담에서 비동기를 제안할 땐, "상태 추적까지"를 같이 말하는 것이 시니어다 — 빠르게 만들되, 문제를 잡을 수 있게까지.
