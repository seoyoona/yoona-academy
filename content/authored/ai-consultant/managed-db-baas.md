지금까지 DB를 '직접 운영한다'고 가정하고 배웠다 — 표를 만들고, 마이그레이션을 돌리고, 백업을 챙기고. 그런데 실제 초기 서비스 대부분은 DB를 **직접 굴리지 않는다**. 관리형 DB(RDS)나 BaaS(Supabase·Firebase)에 맡긴다. PM이 "그럼 직접 안 다루면 이걸 왜 배웠나요?"라고 묻는 건 좋은 질문이다 — 답은, **관리형에 맡겨도 구조(표·관계·트랜잭션)는 우리가 설계하기 때문**이다. 이 레슨은 DB를 직접 운영할 때와 관리형·BaaS에 맡길 때의 차이를 다룬다. 견적·아키텍처 상담에서 빈번하게 나오는 결정이다.

## 직접 운영 vs 관리형 vs BaaS — 세 단계

DB를 두는 방식은 크게 세 단계로 본다:

| 방식 | 예 | PM이 알 한 줄 |
|---|---|---|
| **직접 운영** | EC2 위에 PostgreSQL 직접 설치 | 서버도 우리가, DB 운영도 우리가. 자유도 최대·운영 부담 최대. |
| **관리형 DB** | AWS RDS, Supabase Postgres, Neon | DB 소프트웨어는 우리가 쓰되, 설치·백업·업데이트는 클라우드가. |
| **BaaS** | Supabase(전체), Firebase | DB뿐 아니라 로그인·파일·API까지 '앱 뒷단' 전체를 빌려 쓴다. |

중요한 관찰: **셋 다 내부 결국은 관계형 DB(또는 유사)가 있다.** Supabase도 PostgreSQL이고, RDS도 PostgreSQL이다. 그래서 앞서 배운 표·PK·FK·트랜잭션·SQL은 셋 모두에 그대로 적용된다. 다르면 **누가 운영 노동을 떠안는가**(우리 vs 클라우드)와 **어디까지 빌리는가**(DB만 vs 로그인·파일까지)다.

## 관리형 DB(RDS) — 운영 노동을 '빌리는' 선택

**관리형 DB**는 DB 설치·백업·복제·업데이트·모니터링을 클라우드가 대신해 주는 서비스다(AWS RDS, Supabase Postgres, Google Cloud SQL 등).

직접 운영하면 이런 일을 다 우리가 챙겨야 한다:
- DB 소프트웨어 버전 업데이트
- 매일 백업 스크립트
- 장애 시 복구
- 디스크·메모리 관리
- 보안 패치

관리형은 이 운영 노동을 '빌린다'. **초기 서비스는 거의 항상 관리형이 낫다** — 백업·복구·업데이트를 우리가 손수 하면 그 시간에 기능을 못 만든다. PM 상담에서 "DB는 RDS(또는 Supabase)로"가 기본 추천인 이유다.

단, 관리형도 우리가 설계하는 건 그대로다: 스키마, 표, 관계, 마이그레이션, 쿼리 최적화. **운영은 빌려도 구조 설계는 못 빌린다.** 그래서 앞선 레슨들이 필요한 것이다.

## BaaS(Supabase·Firebase) — 뒷단 전체를 빌리는 선택

**BaaS(Backend as a Service)**는 DB뿐 아니라 **앱에 자주 필요한 뒷단 전체**를 빌려 준다: 로그인(Auth), 파일 저장(Storage), 자동 API, 실시간(Realtime), 가끔 함수(Edge/Cloud Functions).

- **Supabase**: PostgreSQL 기반. "오픈소스 Firebase 대안"을 표방. 로그인 + Postgres + Storage + 자동 API + Realtime을 한 세트로. (이전 Auth·DB 레슨의 BaaS 구현 예로 언급.)
- **Firebase**: Google의 BaaS. 특히 앱 푸시(FCM)·실시간·인증에 강하. 자체 DB(Firestore)는 관계형보다 '문서형'에 가깝다.

왜 BaaS를 쓰는가. **초기 MVP를 가장 빠르게 만들 수 있기 때문**이다. 로그인·CRUD·파일업로드 정도가 필요한 서비스라면, 백엔드 서버를 처음부터 짜는 대신 BaaS로 며칠 만에 띄운다.

## BaaS vs 직접 백엔드 — 언제 뭘?

이 결정이 PM 상담의 단골 메뉴다.

**BaaS(Supabase/Firebase)가 좋을 때:**
- 빠른 MVP. 시장 검증이 먼저.
- 로그인 + DB + 파일 업로드 정도가 핵심.
- 복잡한 비즈니스 로직이 적다.
- AI에서 벡터 검색/RAG까지 붙일 가능성(Supabase는 pgvector 지원).

**직접 백엔드(Node/Express, FastAPI 등)가 좋을 때:**
- 복잡한 규칙·대량 처리(배치·큐·스케줄러)가 많다.
- 외부 연동(PG, ERP, 사내망, 파트너 API)이 많다.
- 강한 보안·감사·권한 요구.
- 고객사 인프라 규정이 있다(특정 클라우드·자체망).
- 성능/비용이 BaaS 한계에 닿았다.

**현실은 섞어 쓰는 경우가 많다.** BaaS로 빠르게 시작하다가, 트래픽/복잡도가 넘어가면 일부를 자체 백엔드로 이관. 중요한 건 "지금 단계에 맞는 선택"이지 "정답"이 아니다.

## RLS(Row Level Security) — BaaS에서 꼭 알아야 한 가지

Supabase 같은 Postgres 기반 BaaS에선 **RLS(Row Level Security)**가 자주 나온다. 한마디로 **"이 사용자는 이 행만 볼 수 있다"를 DB 수준에서 거는 규칙**이다.

예: "회원은 본인 예약만 본다"를 RLS로 걸면, 설령 API를 직접 쳐도 다른 사람의 예약이 안 보인다. 클라이언트에서 보여주기만 숨기는 것(이전 레슨의 클라이언트 vs 서버)과 달리 **DB 자체가 거른다** — 보안이 훨씬 강하다. Supabase를 쓴다면 RLS 설정은 기본 보안 항목이다. PM은 "RLS로 행 단위 권한을 걸었나?"를 Supabase 프로젝트의 기본 질문으로 가져도 좋다.

## worked example: "관리자/사용자 예약 서비스"의 DB 선택 상담

고객: "사용자 예약 + 관리자 화면 + 결제 연동을 원합니다. 초기라 빠르게, 비용도 적게."

추천 흐름:
1. **DB + 로그인**: Supabase(관리형 Postgres + Auth 세트)로 시작 — 백엔드 서버 없이 로그인·CRUD 며칠 안에.
2. **결제**: 결제사(토스/Stripe)를 붙이되, **결제 웹훅 처리와 예약 상태 동기화**는 신뢰가 필요하니 서버사이드(이전 레슨)에서 — Supabase Edge Function이나 작은 백엔드로.
3. **권한**: "관리자만 예약 전체 조회"를 RLS로 걸어, 클라이언트 우회를 막는다.
4. **백업**: Supabase(또는 RDS) 자동 백업 + 보관기간 확인(이전 레슨).
5. **확장**: 트래픽/복잡도가 커지면 결제·배치 부분을 자체 백엔드로 이관, DB는 Postgres 그대로 유지(구조 이전 불필요).

이 상담 한 장에 Phase 1~3의 거의 모든 개념(층, API, CRUD, 인가, 트랜잭션, 백업, RLS)이 녹아 있다. PM 상담력이 결국 이런 "요구 → 구조 → 운영 선택"의 번역이다.

## 흔한 실패 모드와 처방

- **초기부터 직접 백엔드로 over-engineering.** 운영 노동만 커지고 MVP가 늦어진다. 처방: 보통 BaaS/관리형로 시작, 필요해지면 이관.
- **BaaS를 "보안 다 됐다"로 믿는다.** RLS 없으면 클라이언트 우회에 뚫린다. 처방: 행 단위 권한은 RLS로.
- **DB 구조를 BaaS에 맡긴다 착각.** Supabase도 스키마·마이그레이션은 우리가. 처방: 구조 설계(ERD, 정규화, 인덱스)는 여전히 우리 몫.
- **백업을 안 확인한다.** 관리형이라 "되겠지" — 보관기간/복원시간은 꼭 확인. 처방: 백업 정책을 상담 산출물에 포함.

## 상담에 바로 쓰는 한 줄

"DB를 어떻게 둘까"를 물을 때, 기본 추천은 "초기엔 관리형/BaaS, 구조는 우리가 설계, 보안은 RLS/백엔드 인가로"다. 자유도가 필요해지면 그때 직접 운영으로.

## 개발자가 이 단어 말할 때

- **관리형(managed) DB / RDS** — 운영을 클라우드가 대신하는 DB.
- **BaaS / Supabase / Firebase** — 뒷단 전체 빌림.
- **RLS(Row Level Security)** — DB 수준의 행 단위 권한.
- **인스턴스 / 리전** — DB가 도는 서버 단위 / 물리적 위치(예: 서울).
- **이관(migration of backend)** — BaaS에서 자체 백엔드로 옮기는 일(스키마 마이그레이션과 다름).

## ✍️ 산출물 과제

본인(또는 상담 중인) 서비스를 "BaaS로 시작할지, 직접 백엔드로 할지" 결정하고 그 이유를 3문장으로 적어라. 반드시 (1) 로그인 (2) 권한(RLS/백엔드) (3) 백업 보관기간 세 항목에 대해 "어떻게 할 건지"를 한 줄씩 적어라.
