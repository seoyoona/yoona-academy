개발자가 "이 버튼은 HTML로 만들고, CSS로 꾸미고, JS로 움직이게 합니다"라고 말할 때, PM이 세 글자를 같은 "화면 만들기"로 들으면 회의가 엇갈린다. 세 가지는 각자 다른 일을 하고, 고치는 사람도, 공수도, 깨지는 방식도 다르다. 이 레슨은 HTML·CSS·JS의 역할을 구분한 뒤, 그 화면이 최종적으로 클라우드라는 자리에 어떻게 올라가는지까지 한 번에 본다. 목표는 "디자인이 깨졌다"와 "기능이 안 된다"를 서로 다른 버그로 구분할 수 있게 되는 것이다.

## HTML — 뼈와 내용

HTML은 화면의 **뼈와 내용**을 담는다. "여기 제목이 있고, 여기 입력창이 있고, 여기 버튼이 있다"는 구조와 글자를 정의한다. 제목, 문단, 목록, 링크, 입력창, 버튼 — 이런 *무엇이 있는지*를 HTML이 결정한다.

핵심은 HTML이 **"있는 것"**만 정의한다는 점이다. 색깔도 위치도 크기도 여기서 정하지 않는다. 그래서 HTML만 있으면 화면이 하얗고 왼쪽 위에 다닥다닉 붙은, 촌스러운 페이지가 된다. 그래도 *내용 자체*는 다 있다. "내용은 나오는데 예쁘지 않다"면 HTML은 정상이고 CSS 문제다.

## CSS — 생김새

CSS는 **생김새**를 담당한다. 색깔, 크기, 여백, 위치, 글꼴, 반응형(화면 크기에 따라 배치가 바뀌는 것)이 모두 CSS다. "버튼이 파란색이어야 한다", "모바일에서는 세로로, PC에서는 가로로" 같은 것들을 CSS가 한다.

PM이 자주 헷갈리는 지점: **"디자인이 깨졌다"는 거의 항상 CSS의 문제**다. 내용은 다 보이는데 위치나 색이 이상하면 HTML이 아니라 CSS를 본다. 반대로 "버튼 자체가 안 보인다"면 HTML 레벨일 수 있다.

## JavaScript(JS) — 움직임

JS는 화면의 **움직임과 논리**를 담당한다. 버튼을 누르면 입력값을 검사하고, 서버에 요청을 보내고, 결과를 화면에 다시 그린다. "클릭했을 때 무언가 일어나게" 하는 것이 JS다.

앞서 본 프론트엔드 레슨에서 "프론트엔드도 검증과 요청을 한다"고 했는데, 그 일을 하는 것이 JS다. HTML이 정적(가만히 있는)이라면, JS가 붙는 순간 화면은 반응하게 된다. **"기능이 안 된다"는 보통 JS(또는 그 너머 백엔드)의 문제**지, HTML·CSS의 문제가 아니다.

## 세 가지를 한 표로

| 무엇이 | HTML | CSS | JS |
|---|---|---|---|
| 담당 | 뼈·내용 | 생김새 | 움직임·논리 |
| 고장 증상 | 요소가 아예 안 보임 | 예쁘지 않음·위치 이상 | 클릭해도 반응 없음 |
| 질문 | "있는가?" | "예쁜가?" | "움직이는가?" |

이 표를 외울 필요는 없다. 다만 버그 리포트를 받으면 "이건 생김새 문제인가, 움직임 문제인가"를 먼저 묻는 습관이 붙으면 개발자와 대화가 절반으로 줄어든다.

## 프레임워크 — 같은 세 가지를 더 편하게

"React", "Vue", "Next.js" 같은 이름을 듣게 된다. 이들은 HTML·CSS·JS를 **없애는 게 아니라 더 편하게 다루게 해주는 도구**다. 결국 화면에 나오는 것은 여전히 HTML·CSS·JS다. 프레임워크는 반복되는 화면을 부품(컴포넌트)으로 나누고, 데이터가 바뀌면 화면을 자동으로 고쳐 주는 식의 편의를 준다. PM에게 "React 씁니다"는 "HTML·CSS·JS를 React라는 틀 안에서 쓴다"로 들으면 된다.

## 클라우드 — 이 화면이 돌아갈 자리

화면을 만들었다고 끝이 아니다. 그 화면을 사용자가 열려면 **어딘가에 올려둬야(배포) 한다**.

- **정적 화면**(HTML·CSS·JS만)은 파일 자체를 올려두면 된다. Vercel·Netlify 같은 곳에 올리면 끝. 서버 계산이 필요 없으니 싸고 빠르다.
- **동적 서비스**(백엔드·DB가 있는)는 서버와 DB가 돌아갈 자리가 따로 필요하다. 여기에 EC2·RDS·Supabase 같은 이름이 등장한다.

배포(deploy)란 "만든 코드를 사용자가 접근할 수 있는 자리에 옮겨 놓는 일"이다. 개발자가 "배포하겠습니다"라고 하면, 새 화면이 실제 주소(your-service.com)에 반영되는 것이다. **"개발 환경에서는 되는데 배포하면 안 된다"**는 흔한 말은, 코드 자체 문제가 아니라 올려놓는 자리(환경)의 설정 문제일 때가 많다 — 이건 Phase 2(환경변수)와 Phase 5(클라우드)에서 다룬다.

## worked example: "문의 폼"을 세 층으로 보기

고객 요구: "사용자가 이름과 메시지를 적어 보내면, 사장님 메일로 가게 해주세요."

- **HTML**: 이름 입력창, 메시지 입력창, '보내기' 버튼을 만든다. → 이 시점엔 버튼을 눌러도 아무 일도 안 일어난다.
- **CSS**: 입력창에 테두리를, 버튼에 파란 배경을 입힌다. 모바일에서 세로로 보이게 한다. → 예뻐졌지만 여전히 누르면 아무 일도 없다.
- **JS**: '보내기'를 누르면 빈 칸을 검사하고, 서버에 `문의 생성` API로 값을 보낸다. 성공하면 "전송되었습니다"를 띄운다. → **여기서 처음으로 "기능"이 생긴다.**

교훈: 같은 "문의 폼"이어도, 깨짐은 CSS를, 기능 부재는 JS를 본다. 한 버그 리포트에서 "디자인이 이상해요"와 "안 눌러져요"가 같이 오면, 둘은 다른 사람이 다를 수도 있는 별개 작업이다.

## 실 사례(익명화) — 서비스 재구축에서 "생김새가 미세하게 어긋나는" 버그

> 실제 프로젝트 사례를 익명화해 옮겼다. 식별정보는 제거하고 패턴만 남겼다.

한 클라이언트의 서비스를 **직접 코드로 다시 짜는(재구축)** 프로젝트가 있었다. 기존 서비스(노코드로 만들어진)와 새 코드로 만든 화면이 **"똑같이 보이는가"**가 품질 기준이었는데, 문제는 "거의 같은데 어딘가 다르다"는 미세한 차이였다. 팀이 쓴 방법은 **UI parity gap 문서** — 화면을 한 칸한 칸 비교해, 어긋나는 점을 항목별로 기록하고, 발견 시 **스크린샷을 증거로 함께 남기는** 것이었다.

교훈은 이 레슨의 핵심과 직결된다: "예쁜데 원래랑 미세하게 다르다"는 버그의 정체는 거의 다 **CSS layer**(생김새)에 있었다. HTML(내용)은 같아도 여백·색·폰트가 어긋나면 달라 보인다. 반대로 "눌러도 안 된다"는 JS(움직임) 문제. 이 둘을 한 버그로 몰아넣지 않고, "이건 생김새(CSS), 이건 움직임(JS)"으로 나눠 기록했기 때문에 — 누가 뭘 고쳐야 하는지, 얼마나 걸리는지가 보였다. 디자인 시안을 받으면 "이 작업은 생김새(CSS), 이건 움직임(JS)"으로 먼저 나누는 습관이 이 사례의 핵심 실무였다.

## 흔한 실패 모드와 처방

- **"화면 다 했어요"의 함정.** HTML·CSS까지만 끝내놓고 "화면 됐다"고 보고하면, 실제론 JS(기능)가 빠져 있다. 처방: 화면 완성 기준에 "버튼을 누르면 실제로 일어나는가"를 포함시켜라.
- **프레임워크를 기술로 과대평가.** "React라서 더 비싸다"가 아니라 React는 같은 HTML·CSS·JS를 다루는 도구일 뿐이다. 처방: 프레임워크 선택은 유지보수·팀 숙도의 문제지, 기능 자체의 문제가 아니다.
- **배포를 코드의 일부로 안 본다.** "로컬에선 됩니다"로 끝내면 실제 환경에서 안 될 수 있다. 처방: 환경 변수·배포 설정을 별도 산출물로 관리하라(Phase 2·5).

## 상담에 바로 쓰는 한 줄

디자인 시안을 받으면 "이건 생김새(CSS) 작업이고, 이건 움직임(JS) 작업이다"로 먼저 나눠라. 전자는 디자이너·퍼블리셔 영역, 후자는 개발자 영역이라 공수와 담당이 다르다.

## 개발자가 이 단어 말할 때

- **"DOM"**: HTML이 화면에 그려진 구조. JS가 이걸 고쳐 화면을 바꾼다.
- **"반응형"**: 화면 크기에 따라 배치가 바뀌는 것. CSS 영역.
- **"컴포넌트"**: React 등에서 재사용하는 화면 부품.
- **"빌드/배포"**: 코드를 올려놓을 수 있는 형태로 묶고(빌드), 올리는(배포) 일.

## ✍️ 산출물 과제

자주 쓰는 웹사이트 하나를 골라, 그 화면의 요소 세 개를 HTML·CSS·JS로 분해하라. 예: "검색창은 HTML(입력창), 둥근 테두리는 CSS, 엔터 치면 결과가 뜨는 건 JS." 각 요소가 세 단어 중 어디에 속하는지 명시하라.
