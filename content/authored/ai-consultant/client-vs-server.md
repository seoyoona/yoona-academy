"그 코드는 클라이언트에서 도나요, 서버에서 도나요?" — 이 질문 하나로 보안·성능·공수가 갈린다. 같은 "기능"이라도 코드가 어디서 실행되느냐에 따라 사용자가 조작할 수 있는지, 서버 비용이 드는지, 느린지 빠른지가 완전히 달라진다. 이 레슨은 클라이언트사이드와 서버사이드의 차이를 짚고, 각 코드가 깨질 때 증상이 어떻게 다른지 본다. 목표는 "이 로직은 어디서?"를 자연스럽게 묻는 습관을 다는 것이다.

## 클라이언트사이드 — 사용자 기기에서 도는 코드

**클라이언트사이드(client-side)** 코드는 사용자의 기기(브라우저, 앱)에서 실행된다. HTML·CSS·JS가 대표적. 프론트엔드 전부가 이쪽이다.

특징:
- **빠르다**: 서버를 오가지 않고 기기 안에서 즉시 처리. 버튼 누르면 즉시 반응.
- **사용자가 볼 수 있다**: 브라우저 개발자 도구로 코드를 열어볼 수 있다.
- **조작 가능하다**: 사용자가 이 코드를 고쳐서 실행할 수 있다.

마지막 특징이 핵심이다. **클라이언트 코드는 사용자가 마음대로 바꿀 수 있다.** 그래서 "할인율 50% 적용" 코드를 클라이언트에 두면, 사용자가 코드를 고쳐 99% 할인으로 바꿀 수 있다. 신뢰가 필요한 판단은 결코 클라이언트에 둬선 안 된다.

## 서버사이드 — 서버에서 도는 코드

**서버사이드(server-side)** 코드는 회사 서버에서 실행된다. 백엔드의 규칙·계산이 여기서 돈다.

특징:
- **사용자가 못 본다**: 코드가 서버에 있어, 사용자는 요청과 응답만 본다.
- **조작 불가**: 사용자가 서버 코드를 고칠 수 없다.
- **신뢰 가능**: 여기서 내린 판단은 위조하기 어렵다.
- **비용·지연**: 서버 자원을 쓰고, 요청마다 시간이 든다.

"할인율 계산"을 서버에 두면 사용자는 할인율을 못 바꾼다. 결제 금액·권한·재고 확인 같은 것은 무조건 서버사이드여야 한다.

## 한 표로 비교

| 항목 | 클라이언트사이드 | 서버사이드 |
|---|---|---|
| 어디서 | 사용자 기기 | 회사 서버 |
| 속도 | 빠름(즉시) | 상대적으로 느림(요청 필요) |
| 사용자 조작 | 가능 | 불가 |
| 신뢰 | 낮음 | 높음 |
| 비용 | 사용자 부담 | 서버 부담 |
| 깨지면 | 화면이 이상/안 됨 | 기능 자체가 안 됨(에러) |

## "이중 확인(double-check)" 패턴

실무에서는 같은 검사를 **양쪽에 다** 두는 게 정석이다:

- **클라이언트**: 빈 칸 검사 등 — 사용자 친화(빠른 피드백). 편의용.
- **서버**: 같은 검사를 다시 — 신뢰의 최종防线. 보안용.

"왜 같은 검사를 두 번 짜죠?"라는 질문에 답은 "클라이언트 검사는 사용자가 우회할 수 있어서, 진짜 안전은 서버 재검증에 있다"다. 공수가 두 배처럼 보이지만 보안에서는 생략할 수 없는 비용이다.

## worked example: "쿠폰 할인 적용"을 어디서?

고객 요구: "쿠폰 코드 입력하면 결제 금액에서 20% 깎아 줘."

- **틀린 구현(클라이언트만)**: 프론트 JS가 쿠폰 코드를 보고 "20% 할인"을 계산해 결제창에 띄움. → 사용자가 JS를 고쳐 "90% 할인"으로 바꾸거나, 결제 API에는 원금액을 보내면서 화면만 싸게 보이게 할 수 있다. **결제 사고 보장.**
- **맞는 구현(서버)**: 프론트는 쿠폰 코드를 `POST /apply-coupon`으로 보낼 뿐. **서버**가 "이 쿠폰이 유효한가, 20%인가"를 계산하고 최종 금액을 확정. 결제는 그 서버 확정 금액으로만 진행. → 사용자가 흥정할 수 없다.

교훈: 돈·권한·진실(정답)이 걸린 판단은 무조건 서버사이드. 클라이언트는 "보기 좋게"만. 결제 금액을 클라이언트가 정하게 두면, 그 서비스는 사고가 날 때까지 아무도 모르는 사고를 안고 가는 셈이다.

## 렌더링 — 화면을 어디서 그릴까

웹에서는 "화면을 그리는 작업" 자체를 클라이언트·서버 중 어디서 할지도 선택지다:

- **CSR(클라이언트 렌더링)**: 빈 HTML을 보내고 JS가 화면을 그림. 동적 앱에 적합. 첫 화면이 늦을 수 있음.
- **SSR(서버 렌더링)**: 서버가 완성된 HTML을 보냄. 첫 화면 빠르고 SEO(검색노출)에 유리.
- **하이브리드**: Next.js 등은 페이지마다 섞어 쓴다.

PM이 "첫 화면이 느려요"나 "검색에 안 떠요"라는 요구를 받으면, 렌더링 방식(CSR/SSR)이 원인일 수 있다 — 이건 기획 단계에서 "이 페이지는 검색에 노출돼야 하는가?"로 미리 정해 두면 좋다.

구체적으로, 마케팅/랜딩/블로그 같은 페이지는 **검색 노출(SEO)과 첫 화면 속도**가 매출과 직결된다. 이런 페이지를 CSR(빈 HTML + JS로 그림)로 만들면 구글봇이 내용을 제때 못 읽어 검색 순위가 떨어지고, 첫 화면이 흰 배경으로 멈춰 있다. 반면 관리자 대시처럼 "로그인 뒤에만 쓰는 화면"은 검색 노출이 무관하므로 CSR로 충분하다. 즉 렌더링 방식은 단순 기술 선택이 아니라 **"이 페이지의 목적 — 검색에 떠야 하는가, 로그인 뒤인가"**에서 거꾸로 정해지는 기획 결정이다. 상담에서 "이 페이지는 SEO 필요한가요?" 한 질문이 렌더링 공수·구조를 갈라놓는다.

## 실 사례(익명화) — "관리자에만 가격 보이기"를 서버로 넘긴 결정

> 실제 프로젝트 사례를 익명화해 옮겼다.

한 서비스에서 **"관리자 화면엔 금액을 보여주고, 사용자 화면엔 숨긴다"**는 요구가 있었다. 처음엔 화면(클라이언트)에서 숨기면 되는 것처럼 보였다. 하지만 그렇게 하면 누구나 API를 직접 호출해 금액을 빼낼 수 있다 — 클라이언트 코드는 사용자가 고칠 수 있기 때문이다. 그래서 **금액·권한 판단은 서버사이드**로 넘겼다.

교훈: "이 판단을 사용자가 고쳐도 되는가?"라는 질문 하나로 클라이언트/서버가 갈린다 — "아니"면 서버. 이 사례의 "가격 노출"은 전형적인 서버 판단이다. 상담에서 요구를 받으면 "이걸 사용자가 임의로 바꾸면 안 되나?"를 먼저 묻는 습관이 보안의 출발점이다.

## 흔한 실패 모드와 처방

- **신뢰 판단을 클라이언트에 둔다.** 권한·금액·정답 검사를 프론트에만 두면 우회 공격에 뚫린다. 처방: "이걸 사용자가 고치면 안 되나?"를 물어 보고, 그렇다면 서버로.
- **모든 걸 서버에 둬서 느리다.** 입력 검증 같은 가벼운 피드백까지 서버만 기다리면 UX가 나빠진다. 처방: 가벼운 검사는 클라이언트(편의) + 서버(신뢰) 이중으로.
- **CSR만 써서 SEO가 안 된다.** 마케팅 페이지가 검색에 안 뜬다. 처방: 노출이 중요한 페이지는 SSR/하이브리드로.
- **"보이지 않으면 안 된다"로 착각한다.** 프론트에서 숨긴 버튼이 보안이라 믿지만, 서버 인가가 없으면 누구나 API를 직접 호출해 실행한다. 처방: 화면 숨김은 편의, 보안은 항상 서버사이드 인가 검사로.

## 상담에 바로 쓰는 한 줄

기능을 받으면 "이 판단은 사용자가 고칠 수 있어도 되나?"를 묻자. "아니"면 서버사이드, "상관없다"면 클라이언트사이드다.

## 개발자가 이 단어 말할 때

- **"프론트/백"**: 클라이언트/서버의 줄임말.
- **"검증(validation)"**: 입력값 확인. 보통 양쪽에 둔다.
- **"CSR/SSR/SSG"**: 화면을 그리는 시점(클라이언트/서버/빌드).
- **"우회(bypass)"**: 클라이언트 검사를 사용자가 무시하는 것.
- **"비밀값(secret)은 서버에"**: 클라이언트 코드에 넣으면 누구나 본다.

## ✍️ 산출물 과제

본인 서비스의 한 기능에서 "서버사이드여야 하는 판단 1개"와 "클라이언트사이드여도 되는 판단 1개"를 각각 골라, 그 이유를 한 줄씩 적어라. 보안·돈·권한이 걸린 것이 서버 후보다.
