BaaS로 MVP를 빠르게 띄웠다. 그런데 사용자가 늘고, 기능이 복잡해지고, 결제·배치·외부 연동이 붙기 시작한다. 어느 순간 "Supabase 자동 API만으로는 안 되는데…"라는 벽에 부닥친다. 이 레슨은 BaaS의 한계가 어디서 오는지, 언제 자체 백엔드로 이관해야 하는지, 그리고 이관이 반드시 "전부 갈아엎기"가 아님을 다룬다. "BaaS로 시작했다"가 "BaaS에 갇혔다"가 되지 않게 하는 설계 감각이 핵심이다.

## BaaS의 네 가지 한계

빠른 MVP의 대가로, BaaS에는 명확한 한계가 있다:

1. **복잡한 비즈니스 로직의 한계**: 자동 API는 "표 CRUD"엔 강하지만, "엑셀 업로드 → 검증 → 대량 발송 → 실패 리포트" 같은 다단계 흐름엔 약하다. 이런 건 작은 서버 코드(Edge Function)로 우회해야 하는데, 점점 커지면 그게 또 백엔드가 된다.
2. **비용 폭발**: BaaS는 사용량(읽기·쓰기·대역폭·함수 호출) 과금이다. 초반엔 싸지만, 트래픽이 늘면 "직접 굴리는 게 싸다"로 역전된다.
3. **성능 통제의 제약**: 쿼리 최적화·인덱스·커넥션 풀 등을 우리 마음대로 못 할 때가 있다. 대량 트래픽에서 병목이 생겨도 손쓸 공간이 좁다.
4. **벤더 종속**: BaaS 기능(자동 API·RLS·Realtime) 깊게 쓸수록 다른 곳으로 옮기기 어렵다. "Supabase 없이는 안 돌아간다"가 되면 협상력도 떨어진다.

## 언제 이관 신호인가 — 다섯 가지 징후

전부 한꺼번에 오지 않는다. 하나씩 나타난다:

- **복잡 로직이 자꾸 Edge Function으로 빠져나간다.** 어느 순간 그 함수들이 또 하나의 백엔드처럼 부풀어 있다.
- **월 사용료가 감당 안 된다.** 트래픽 증가 → 과금 폭발 → 직접 운영이 더 싸다는 게 계산으로 드러난다.
- **성능 불만이 쌓인다.** "느려요"가 잦은데, BaaS 안에서는 최적화 손이 안 닿는다.
- **강한 보안/감사 요구가 생긴다.** 고객사 규정·감사로그·커스텀 권한 트리 등 BaaS 정책으로 못 표현할 만큼 복잡해진다.
- **외부 연동이 많아진다.** PG·ERP·사내망·파트너 API 연동이 많아지면 어차피 자체 백엔드가 필요해진다.

이 중 2개 이상이 겹치면 이관을 진지하게 검사할 때다.

## 이관은 '전부 갈아엎기'가 아니다 — 점진적

오해하면 안 되는 점: **DB까지 버리고 새로 짜는 게 아니다.** Supabase의 DB는 **Postgres**다. 따라서:

- **DB는 그대로** — Supabase의 Postgres를 직접 운영하는 관리형 Postgres(AWS RDS, Neon 등)로 옮기거나, 심하면 그대로 Supabase DB만 쓰고 API만 자체로.
- **자동 API → 자체 API** — 복잡 로직이 필요한 부분만 자체 백엔드(Node/Express·FastAPI)를 짜서 그 부분만 가져간다.
- **점진적 교체** — 한 기능씩 BaaS에서 자체 백엔드로 옮긴다. "결제·배치는 자체, 나머지는 BaaS" 같은 혼합이 흔하다.

핵심 통찰: **"데이터 모델(Phase 3 ERD)을 표준 Postgres로 잡아두면 이관 부담이 작다."** Supabase가 Postgres 기반인 이유가 여기에 있다 — BaaS를 벗어나도 표·관계·쿼리가 그대로 살아 있다. 반대로 Firebase(Firestore, 문서형)는 관계형이 아니라 이관이 더 무겁다. 초기 선택이 이탈 비용을 결정한다.

## worked example: "예약 서비스"의 이관 시나리오

상황: Supabase로 시작한 예약 서비스가 커져서 (1) 엑셀 대량 업로드+발송, (2) 결제 웹훹 처리, (3) 트래픽 과금 폭발이 겹쳤다.

점진 이관:
1. **DB 유지**: 예약·사용자 표(Postgres)는 그대로. Supabase Postgres → AWS RDS Postgres로 옮기거나 일단 그대로.
2. **복잡 로직만 자체 백엔드**: 엑셀 업로드·파싱·대량 발송·결제 웹훹은 Node/Express(또는 FastAPI)로 짠다. 이 부분은 트랜잭션·큐(Phase 6)가 필요하니 자체 백엔드가 자연스럽다.
3. **나머지는 BaaS 유지**: 단순 조회성 API·프로필은 여전히 Supabase 자동 API + RLS로.
4. **RLS → 백엔드 인가**: 자체 백엔드로 옮긴 부분은 권한을 백엔드 코드에서(Phase 2 인가)로. RLS는 보조로 남겨둘지 결정.

결과: 전부 갈아엎지 않고, 병목/비용/복잡도가 집중된 부분만 이관. DB 구조(ERD)는 그대로 살아 있어 재설계 비용이 거의 없다. **좋은 초기 설계(Postgres 기반)가 이탈 비용을 낮춘다**는 교훈이 이 시나리오에 다 들어 있다.

## 흔한 실패 모드와 처방

- **이관을 "전부 새로"로 생각해 미룬다.** 비용이 커서 방치 → 한계가 더 심해진다. 처방: 점진적, 부분적 이관. 한 기능씩.
- **DB까지 버린다.** BaaS 종속 DB가 아니었다면(= Postgres였다면) DB는 살린다. 처방: 이관 대상을 "API/로직"과 "DB"로 분리해 판단.
- **초기에 비표준 구조로 깊이 간다.** Firebase 문서형으로 관계를 억지로 표현하면 이탈이 고통스럽다. 처방: 관계형 데이터가 중심이면 Postgres 기반 BaaS(Supabase)로 시작.
- **비용을 안 본다.** "지금 싸니까" 계속 BaaS → 어느 날 과금 폭발. 처방: 사용량-비용 임계점을 정기 점검.

## 상담에 바로 쓰는 한 줄

"MVP는 BaaS로"를 말할 때, "나중에 커지면 어느 부분부터 자체 백엔드로 옮길 수 있는지"를 한 줄로 덧붙여라. 이탈 비용을 설계 단계에서 언급하는 것이 시니어 상담이다.

## 개발자가 이 단어 말할 때

- **이관(migration of backend)** — BaaS에서 자체 백엔드로 옮기는 일 (스키마 마이그레이션과 다름).
- **벤더 종속 / lock-in** — 특정 BaaS에 묶여 빠져나오기 어려운 정도.
- **관리형 Postgres(RDS, Neon)** — 운영은 클라우드가, 구조는 우리가.
- **점진적 이관 / strangler 패턴** — 한 부분씩 교체해 나가는 방식.
- **사용량 과금** — 호출/대역폭/저장량에 비례해 청구되는 비용 모델.

## ✍️ 산출물 과제

본인 서비스에서 "BaaS로 시작했을 때 가장 먼저 자체 백엔드로 옮길 만한 기능" 하나를 고르고, 그 이유(위 다섯 징후 중 어디에 해당하는지)를 적어라. 그리고 "DB는 이관에서 어떻게 처리할지"(유지/이동)를 한 줄로 결정하라.

## 한 걸음 더 — 이관 비용은 '얼마나 깊이 썼나'에 비례한다

이관이 얼마나 아플지는 **BaaS 기능에 얼마나 깊이 의존했느냐**로 정해진다. 표준 SQL과 Postgres 구조만 썼다면 DB는 그대로 옮기면 끝 — 거의 무통장. 하지만 자동 API·Realtime·RLS 정책을 깊게 썼다면, 그것들을 자체 백엔드로 다시 구현해야 하므로 공수가 커진다. 즉 **"이탈이 쉬운 구조로 쓰는 것" 자체가 설계 결정**이다: BaaS 기능을 쓸 때도 "이걸 나중에 직접 구현할 수 있을까"를 한 번 생각하며 쓰면, 종속을 최소화할 수 있다. "빠르게 쓰되, 나중에 빠져나오기 쉽게 쓴다"는 균형 감각이 시니어의 BaaS 운용법이다.
