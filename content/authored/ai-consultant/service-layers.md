고객이 "예약 앱 하나 만들어주세요"라고 할 때, 그 문장을 그대로 개발자에게 넘기면 프로젝트는 거의 항상 삐걱거린다. "화면"이 어디까지인지, "데이터"는 어디에 쌓이는지, "알림"은 누가 보내는지가 정해져 있지 않기 때문이다. 이 하나의 문장을 **화면·서버·데이터베이스·API·클라우드**라는 층으로 쪼갤 수 있으면, 견적·일정·리스크가 잡히고 개발자와 같은 언어가 된다. 이 레슨은 그 쪼개기 — 서비스가 왜 여러 층으로 나뉘는지 — 를 다룬다. 코드를 짤 필요는 없다. 다만 어느 층에서 어느 문제가 생기는지를 말로 설명할 수 있어야 한다.

## 프론트엔드 — 사용자가 만지는 층

프론트엔드는 사용자가 직접 보고 누르는 모든 것이다. 웹이면 브라우저에 뜨는 화면, 앱이면 폰에서 터치하는 화면. 버튼, 입력창, 목록, 알림 창이 모두 이 층에서 그려진다.

중요한 점은 프론트엔드가 **"보여주기"만 하는 게 아니라는 것**이다. 사용자가 입력한 값을 검증하고(빈 칸 확인), 서버에서 받아온 데이터를 화면에 맞게 배치하고, 클릭했을 때 어디로 요청을 보낼지 결정한다. 다만 이 층은 **사용자 기기 안에서** 도는 것이 핵심이다. 브라우저나 앱이 꺼지면 같이 사라진다.

PM이 프론트엔드에서 놓치는 것: "화면이 느리다"는 불만의 원인이 화면 자체가 아니라 서버 응답·이미지 크기·데이터 양인 경우가 대부분이다. 층을 알면 원인을 층별로 나눠 본다.

## 백엔드 — 규칙이 도는 층

백엔드는 사용자가 안 보는 곳에서 **규칙을 계산하는 서버**다. "예약 가능한 시간인가", "이 사용자는 관리자인가", "결제는 성공했는가" — 이런 판단이 여기서 일어난다.

프론트엔드가 사용자의 말을 듣고 화면을 그린다면, 백엔드는 그 요청을 받아 **규칙을 적용하고 데이터베이스에 저장·조회**한다. 사용자가 "예약할게요" 버튼을 누르면, 실제로 예약이 되는 일은 백엔드에서 일어난다. 프론트엔드는 "요청했을 뿐"이다.

왜 프론트엔드에서 바로 처리하지 않고 굳이 서버를 거칠까. 규칙을 사용자 기기에 두면, 사용자가 마음대로 규칙을 바꿀 수 있기 때문이다. "결제 완료됨"을 프론트엔드에서 결정하면 누구든 이를 조작해 무료로 결제를 완료할 수 있다. **신뢰가 필요한 판단은 사용자 손이 닿지 않는 서버에** 둬야 한다. 이 한 줄을 이해하면 "왜 이 기능은 서버까지 가야 하죠?"라는 질문에 답이 된다.

## 데이터베이스 — 사실이 쌓이는 층

데이터베이스는 **사실을 영속적으로 저장하는 곳**이다. 사용자, 예약, 결제, 알림 내역이 여기 쌓인다. 서버가 꺼져도, 사용자가 앱을 지워도, 데이터베이스에 있는 사실은 남는다. 그래서 "데이터가 날아갔다"는 말은 거의 항상 데이터베이스의 문제이지 프론트엔드의 문제가 아니다.

데이터베이스는 보통 **테이블**이라는 표 단위로 데이터를 담는다. users, reservations, payments처럼 주제별로 표가 나뉘고, 각 표는 행(row) 하나가 한 건의 사실을 의미한다. 이 구조를 잡는 일을 "데이터 모델링"이라 부르고, PM 상담력의 핵심이 이 층에 있다. (Phase 3에서 다룬다.)

## API — 층과 층을 잇는 계약

API(Application Programming Interface)는 프론트엔드와 백엔드가 **어떤 형식으로 대화할지 정한 계약**이다. "예약 생성" API는 "이런 값을 주면, 이런 결과를 돌려주겠다"는 약속이다.

API가 왜 필요한가. 프론트엔드와 백엔드가 같은 프로그램 안에 있으면 계약이 필요 없다. 하지만 현실에서는 화면은 브라우저·앱에 있고 규칙은 서버에 있으니, 둘을 이어주는 표준화된 문(-door)이 필요하다. 그 문이 API다. API가 명확하면, 화면을 바꾸지 않고 서버 규칙만 고칠 수 있고, 반대로 서버를 건드리지 않고 새 화면(예: 관리자 화면)을 붙일 수 있다. **"API가 왜 필요한가"에 대한 답은 "층을 독립적으로 바꿀 수 있게 하려고"**다.

## 클라우드 — 이 층들이 돌아갈 자리를 빌리는 일

클라우드(AWS, Vercel, Supabase 등)는 위 층들이 **실제로 돌아갈 컴퓨터·저장소·네트워크를 빌려 쓰는 곳**이다. 서버 컴퓨터를 직접 사서机房에 두는 대신, 남이 관리하는 인프라를 쓴다. PM에게 클라우드는 "우리 서비스가 돌아가는 물리적 자리를 우리가 안 사고 빌린다"는 한 줄로 충분하다. (Phase 5에서 EC2·RDS·S3·VPC·IAM을 다룬다.)

## 층별 산출물과 상담 질문

| 층 | 대표 산출물 | 상담에서 물어볼 질문 |
|---|---|---|
| 프론트엔드 | 화면 목록, 화면 설계 | "관리자 화면도 필요한가요, 사용자만인가요?" |
| 백엔드 | 기능 목록, 규칙 정의 | "결제 실패 시 어떻게 처리하나요?" |
| 데이터베이스 | 데이터 모델(ERD) | "예약 내역은 몇 년까지 보관하나요?" |
| API | API 목록(명세) | "외부(파트너)에서도 이 데이터를 쓰나요?" |
| 클라우드 | 인프라 구성, 배포 | "트래픽이 몰릴 때를 대비해야 하나요?" |

## 실 사례(익명화) — 한 예약 서비스 클라이언트를 5층으로 쪼갠 견적

> 아래는 실제 상담 사례를 **익명화**해 옮긴 것이다. 클라이언트·실무자·식별정보는 바꿨고, 구조를 결정한 **판단 흐름**만 남겼다.

상황: 한 클라이언트가 "사용자가 날짜를 골라 예약하고, 관리자는 따로 화면에서 확인하는 서비스"를 원했다. 기존엔 간단히 만들어 쓰던 것을, 트래픽과 요구가 커지면서 **본격적으로 다시 짜는(재구축) 프로젝트**로 가져왔다. 첫 단계는 이 요구를 5층으로 쪼개 보는 것이었다.

1. **프론트엔드**: 사용자 예약 화면 + 관리자 확인 화면. 핵심은 **화면이 둘**이라는 점 — 요구는 "예약 하나"처럼 들렸지만, 실제론 사용자·관리자 **두 역할**의 화면이 필요했다. 여기서 공수가 갈린다.
2. **API**: `예약 생성`, `예약 목록 조회`. 관리자 조회는 **권한이 다른 문**이라 사용자용과 분리해 설계(Phase 2 인가·Phase 4 RLS).
3. **백엔드**: "그 시간에 이미 예약이 있는가?"를 **서버에서** 판단. 이걸 프론트에 맡기면 누구나 중복 예약을 만들 수 있다 — 신뢰 판단은 반드시 백엔드.
4. **데이터베이스**: users, reservations(시간·사용자·상태), availability_slots(예약 가능 시간). 최소 세 표.
5. **클라우드**: 서버·DB가 24시간 돌 자리 + 기존 데이터를 옮겨 올 이관 경로까지 잡아야 했다(Phase 5).

실제 상담에서 짚은 두 결정이 이 5층 안에서 모습을 드러냈다:

- **"관리자 화면에선 내역·금액이 보여도, 사용자 화면에선 일부를 숨긴다"**는 요구. 이건 프론트에서 숨기는 게 아니라 **권한(RLS/백엔드 인가)**으로 가야 한다 — 그래야 API를 직접 쳐도 안 보인다(Phase 2·4).
- **"AI로 자동화를 넣자"**는 아이디어가 있었으나, 검토 결과 **그 서비스에선 효과가 없어 빼기로** 했다. "AI가 무조건 들어가야 하는 건 아니다"는 실제 회의에서 나온 결론이었다(Phase 6).

이렇게 쪼개니 "예약 서비스"라는 한 문장이 — **화면 2종, API 2~3개, 표 3개, 권한 분기 1곳, 데이터 이관 1건**으로 보였고, 비로소 견적과 일정이 잡혔다. 고객의 한 문장을 5층으로 번역하는 것이 상담의 첫째 일이다.

## 흔한 실패 모드와 처방

- **한 층을 빼놓고 견적을 낸다.** "화면만 만들면 되죠?"라고 생각해 백엔드·DB 공수를 안 잡는 경우. 처방: 어떤 요구든 최소 프론트·백엔드·DB 세 층의 일로 쪼개 보라. 한 층이라도 "없다"고 나오면 요구를 다시 보라는 신호다.
- **신뢰 판단을 프론트엔드에 둔다.** 권한·결제·할인 같은 판단을 화면에서 처리하려 하면 보안 구멍이 생긴다. 처방: "이 판단을 사용자가 바꾸면 안 되는가?"라고 물어보고, 그렇다면 백엔드로 보낸다.
- **API를 "나중에"로 미룬다.** API 없이 화면과 서버를 구겨 넣으면, 두 번째 화면(관리자 등)을 붙일 때 처음부터 다시 짜야 한다. 처방: 화면이 하나뿐이어도 프론트·백엔드 사이에 API 계약을 먼저 정의하라.

## 상담에 바로 쓰는 한 줄

고객의 요구를 들으면 "이게 화면인가, 규칙인가, 데이터인가?"로 먼저 분류하라. 그 세 단어로 안 나뉘는 요구는 아직 구체화되지 않은 것이다.

## 개발자가 이 단어 말할 때

- **"프론트/백"**: 화면층 / 서버층.
- **"엔드포인트"**: API의 문 주소. `/reservations` 같은 것.
- **"상태(state)"**: 어디에 값이 있는가. 프론트 상태(화면 안) vs 서버 상태(DB).
- **"영속화(persist)"**: 데이터를 DB에 남겨 두는 일.

## ✍️ 산출물 과제

본인이 상담했거나 상상하는 서비스 하나를 골라, 그것을 프론트엔드·백엔드·데이터베이스·API·클라우드 다섯 층으로 쪼개 보라. 각 층에 한 문장씩만 적되, 반드시 "이 판단은 왜 서버(백엔드)에 있어야 하는가"를 한 군데 이상 명시하라. 화면만 있는 서비스는 없으니, 백엔드와 데이터베이스 층이 비어 있으면 요구를 다시 쪼개야 한다.
