"로그인 만들어주세요"라는 요구는 겉보기엔 하나지만, 실제로는 "누구인지 밝히는 일(인증)"과 "무엇을 할 수 있는지 정하는 일(인가)" 두 개로 나뉜다. 그리고 그 뒤에는 항상 "비밀값(secret)"이 따라다닌다 — 개발자가 "JWT 시크릿이랑 세션 키 주세요"라고 할 때, 그건 사치가 아니라 로그인이 돌아가기 위한 필수 부품이다. 이 레슨은 인증·인가의 차이, session과 token의 두 모델, 그리고 PM이 "왜 시크릿을 달라 하는가"에 대한 답을 다룬다.

## 인증(Authentication) vs 인가(Authorization) — 자주 섞이는 두 단어

- **인증(인증, AuthN)**: "너 누구야?" — 신원을 확인. 아이디/비밀번호로 "이 사람이 회원이 맞다"를 증명.
- **인가(인가, AuthZ)**: "이거 해도 돼?" — 권한을 검사. "이 사람은 관리자라 공지를 지울 수 있다."

이 둘을 구분해야 "관리자 기능"이 이해된다. 일반 회원도 인증(로그인)은 하지만, 공지 삭제는 **인가** 단계에서 막힌다. "로그인했는데 왜 이 버튼이 안 보이죠?"라는 질문의 답은 대개 "인증은 됐지만 인가(권한)가 안 된다"다. PM은 기획서에 "이 화면은 누가(인증) 볼 수 있고, 이 행동은 누가(인가) 할 수 있는가"를 항상 따로 적어야 한다.

## 로그인 다음의 문제: "다음 요청부터 네가 누군지 어떻게 알까?"

HTTP는 **무상태(stateless)**다 — 서버가 매 요청을 처음 보는 것처럼 처리한다. 그래서 로그인 한 뒤에도, 다음 클릭(요청)에서 "나 로그인한 사람이야"를 **매번 다시 증명**해야 한다. 이걸 가능하게 하는 두 가지 방법이 session과 token이다.

## Session 모델 — 서버가 기억

**세션(session)**: 서버가 "이 사용자는 로그인됨"을 **서버 측에 기억**해 두고, 사용자에게는 그 기억을 가리키는 짧은 열쇠(세션 ID)만 쿠키로 준다.

- 흐름: 로그인 → 서버가 세션 저장소에 "사용자 123, 로그인됨" 기록 → 사용자에게 세션 ID 쿠키 발급 → 이후 요청마다 쿠키가 서버에 "나 123이야"를 전달 → 서버가 저장소에서 확인.
- 장점: 서버가 주도권을 쥔다. 로그아웃·강제 퇴출이 쉽다(저장소에서 지우면 끝).
- 단점: 서버에 저장소가 필요하고, 서버가 늘어나면 세션 공유 문제가 생긴다.

## Token 모델(JWT) — 열쇠를 사용자가 쥐

**토큰(token), 특히 JWT**: 서버가 "이 사람은 ~다"라는 **서명된 열쇠**를 만들어 사용자에게 준다. 사용자가 매 요청마다 이 열쇠를 갖고 온다. 서버는 열쇠의 **서명**을 확인(저장소 조회 없이)해 진짜인지 검증한다.

- 흐름: 로그인 → 서버가 JWT(사용자 정보 + 서명)를 **비밀 키(JWT 시크릿)**로 서명해 발급 → 사용자가 보관 → 이후 요청마다 JWT를 헤더에 담아 전송 → 서버가 같은 비밀 키로 서명이 맞는지 확인.
- 장점: 서버가 상태를 기억할 필요 없다. 모바일 앱·여러 서버에 유리.
- 단점: **열쇠가 탈취되면 만료될 때까지 막기 어렵다.** (그래서 만료 시간을 짧게, + 갱신 토큰(refresh token)을 따로 두는 패턴이 흔하다.)

## 왜 시크릿(secret)이 필요한가 — 이 레슨의 핵심 질문

JWT는 서명으로 진짜임을 증명한다. 그런데 **누구나 서명할 수 있으면 JWT는 의미가 없다** — 악의적 사용자가 "나 관리자야"라고 서명해 버리면 끝이니까. 그래서 서명에는 **서버만 아는 비밀값(JWT 시크릿)**이 쓰인다. 이 비밀값을 모르면 서명을 못 만들고, 그래야 서버가 "이 JWT는 내가 서명한 게 맞다"를 신뢰한다.

**이게 개발자가 "JWT 시크릿 주세요"라고 하는 이유다.** 로그인 시스템을 만들려면 반드시 서명용 비밀값이 필요하고, 이 값은 **코드에 직접 쓰지 않고 환경변수로** 넣는다(비밀값이 코드/Git에 올라가면 누구나 서명할 수 있어 시스템이 뚫린다 — Phase 1 Git 레슨 참고). 비슷하게 DB 비밀번호, 외부 API 키, 결제사 시크릿도 모두 환경변수로 다룬다.

PM이 상담에서 "보안 얼마나 들어가요?"라는 질문을 받으면, 최소한의 답은 "비밀값은 환경변수로만, 코드에 하드코딩 금지, 만료/권한은 백엔드에서"다. 이 세 줄이 지켜지면 대부분의 beginner 보안 사고는 막힌다.

## worked example: "관리자 공지 삭제"에서 인가가 작동하는 흐름

고객 요구: "일반 회원은 공지를 보기만 하고, 관리자만 지울 수 있게."

1. 로그인 → 서버가 JWT(사용자 ID + role: "admin" 또는 "member")를 비밀 키로 서명해 발급.
2. 관리자가 삭제 버튼 → 프론트가 `DELETE /notices/5`를 **JWT와 함께** 보냄.
3. 백엔드:
   - **인증**: JWT 서명이 진짜인지 비밀 키로 확인 → "이 사람은 사용자 1, 역할 admin"
   - **인가**: `role === "admin"`인가? 맞으면 → DB에서 공지 5 삭제.
4. 일반 회원이 같은 요청을 보내면, 인증은 통과해도 **인가에서 막힘** → `403 Forbidden`.

핵심: "삭제 권한" 판단은 **백엔드**에서 일어난다. 프론트에서 일반 회원에게 버튼을 안 보여 주는 건 편의일 뿐, 보안은 백엔드의 인가 검사가 한다. 프론트만 믿으면 누구나 API를 직접 쳐서 삭제할 수 있다.

## 실 사례(익명화) — 관리자/일반 사용자의 "보이는 데이터"를 가른 권한

> 실제 프로젝트 사례를 익명화해 옮겼다.

한 서비스에선 **같은 데이터를 관리자와 일반 사용자가 다르게** 봤다 — 관리자는 전체(금액·내역 포함), 일반 사용자는 제한된 화면만. 이 분리를 **프론트 숨김이 아니라 백엔드 인가**로 처리했다. 그리고 토큰 서명에 쓰는 **JWT 시크릿은 환경변수**로만 뒀다 (코드/Git에 박으면 누구나 서명을 만들어 권한을 위조할 수 있으므로).

교훈: "왜 시크릿을 달라 하느냐"의 답이 이 사례에 있다 — 로그인 토큰의 서명에 **서버만 아는 비밀값**이 필요하기 때문이다. 그리고 "관리자만 본다"는 판단은 화면 숨김이 아니라 **백엔드 인가 검사**에 둬야 API를 직접 쳐도 안 뚫린다(Phase 4 RLS로 더 단단해진다).

## 흔한 실패 모드와 처방

- **인가를 프론트에만 둔다.** 화면에서 버튼을 숨기는 걸로 권한을 막았다 착각. 처방: 모든 민감한 행동(삭제·수정·관리 화면 데이터)은 백엔드에서 역할을 다시 검사하라.
- **JWT 시크릿을 코드에 박는다.** Git에 한 번 올라가면 끝. 처방: 무조건 환경변수, `.gitignore`에 `.env` 필수.
- **토큰 만료가 없다.** 탈취되면 영구 권한. 처방: 짧은 만료(1~2시간) + 갱신 토큰.
- **비밀번호를 평문으로 저장한다.** 절대 금물. 처방: bcrypt 같은 해시로만 저장(저장된 값으로는 원래 비밀번호를 알 수 없어야 한다).

## 상담에 바로 쓰는 한 줄

"권한 있는 사람만"이라는 요구가 들어오면, "이 권한 검사는 백엔드에서 하나요?"를 물어라. 프론트에만 의존하면 보안 구멍이다.

## 개발자가 이 단어 말할 때

- **"AuthN/AuthZ"**: 인증/인가.
- **"세션/쿠키"**: 서버 기억 모델. 쿠키는 브라우저에, 세션은 서버에.
- **"JWT/Bearer"**: 토큰 모델. "Bearer xxx"는 요청 헤더에 토큰을 싣는 형식.
- **"환경변수(env)"**: 비밀값을 코드 밖에 두는 창고. 다음 레슨에서 상세.
- **"해시/솔트"**: 비밀번호를 안전하게 저장하는 방법.

## ✍️ 산출물 과제
