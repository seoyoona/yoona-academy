EC2·S3·RDS를 알았다. 그런데 "누가 이 자원에 접근할 수 있는가"를 안 정하면, 클라우드 자원은 인터넷에 다 노출된 채로 돌아간다. DB가 인터넷에 열려 있으면 누구나 접속을 시도하고, 권한이 넓으면 한 키 유출로 전체 계정이 털린다. 이 레슨은 AWS의 두 보안 축 — **VPC**(사설망)와 **IAM**(권한) — 을 다룬다. "우리 자원을 안전하게 가두고, 누가 뭘 할 수 있는지 정하는" 레슨이다. 보안 상담에서 빠지면 안 되는 두 단어.

## VPC — 우리만의 '사설망'

**VPC(Virtual Private Cloud)**는 AWS 안에 만드는 **논리적으로 격리된 사설 네트워크 공간**이다. 한마디로 "인터넷에 직접 노출된 채로 두지 않고, 우리 자원을 우리만의 사설망 안에 가둔다."

VPC가 없다면: EC2/RDS가 인터넷에 바로 붙어, 전 세계 누구나 접속을 시도할 수 있다 — 해킹 시도의 표적이 된다.

VPC가 있으면: 자원을 사설망(예: `10.0.0.x`)에 두고, **인터넷에서 들어오는 문(gateway)**과 **어느 트래픽을 허용할지(보안그룹)**만 통제한다. DB(RDS)는 사설망 안에만 두고 인터넷에 아예 안 열 수 있다 — 앱 서버(EC2)를 통해서만 접근. 이게 기본 보안 구성이다.

PM 식 요약: "VPC = 우리 자원을 사설망에 가두고, 인터넷 노출을 최소화하는 울타리."

## 보안그룹 — '방화벽' 규칙

**보안그룹(Security Group)**은 각 자원(EC2, RDS) 앞에 두는 **방화벽 규칙**이다 — "이 포트로, 어디서 오는 트래픽만 허용한다."

예:
- EC2 보안그룹: "웹 트래픽(80/443)은 인터넷 어디서나 허용." (사용자가 접속해야 하니까)
- RDS 보안그룹: "DB 포트는 **EC2 보안그룹에서 오는 것만** 허용." (앱 서버만 DB에 닿게, 인터넷은 차단)

이 한 줄 — "DB는 앱 서버에서만 접속 허용" — 이 클라우드 보안의 기본이다. DB가 인터넷에 열려 있으면 매초 수천 건의 무차별 접속 시도를 받는다.

## IAM — '누가 무엇을' 권한

**IAM(Identity and Access Management)**은 **AWS 자원에 누가/어떤 서비스가 무슨 권한을 갖는지** 정하는 시스템이다. "이 사용자는 S3 읽기만", "이 앱은 RDS 쓰기만" 식으로 권한을 최소화한다.

왜 중요한가. AWS 계정 전체를 뚫으면 **모든 자원**(EC2·RDS·S3 전부)이 한꺼번에 노출된다. 그래서:
- **루트 계정**은 일상적으로 안 쓰고 2단계 인증(2FA)으로 잠가둔다.
- **최소 권한 원칙**: 각 사용자/서비스는 필요한 최소 권한만. "전체 접근(Admin)"을 습관적으로 주면 위험.
- **서비스 역할(role)**: EC2 앱이 S3에 접근할 땐 비밀번호 대신 '역할'을 줘서, 키를 코드에 박지 않게.

PM 식 요약: "IAM = 누가 어디까지 할 수 있는지 정하는 권한 시스템. 최소 권한이 철칙."

## 보안의 두 축 — VPC(어디서) + IAM(누가)

두 개를 묶어 보면 AWS 보안의 전체가 보인다:

| 축 | 질문 | 도구 |
|---|---|---|
| **네트워크** | 어디서 들어올 수 있나? | VPC + 보안그룹 |
| **권한** | 누가 무엇을 할 수 있나? | IAM |

VPC는 "어디서(네트워크) 접근 가능한가"를, IAM은 "누가(신분) 무엇을 할 수 있는가"를 다룬다. 둘 다 있어야 안전하다. 어느 하나만으로는 부족 — 네트워크만 막아도 권한이 넓으면 내부자/토큰 유출에 뚫리고, 권한만 좁혀도 네트워크가 열려 있으면 무차별 공격에 시달린다.

## worked example: "안전한 3계층" 구성

고객: "DB가 털리면 안 되는 서비스."

권장 구성:
1. **VPC 안에 자원 배치**: EC2(앱), RDS(DB)를 사설망에.
2. **RDS는 인터넷에 완전 차단**: 보안그룹이 "EC2에서 오는 DB 트래픽만" 허용. 인터넷에서 DB 직접 접속 불가.
3. **EC2는 웹 포트만 개방**: 보안그룹이 "80/443은 어디서나" 허용, 나머지는 차단.
4. **IAM 최소 권한**: EC2에 S3 접근 '역할'만 부여, 루트 키는 안 씀, 모든 사람은 2FA.
5. **비밀값은 환경변수**: DB 비밀번호·API 키는 코드에 안 박고 환경변수/Secret Manager(Phase 2·5 다음 레슨).

"DB 털리면 안 돼"가 VPC 격리 + 보안그룹 + IAM 최소권한 + 환경변수로 번역된다. 이 다섯 단어가 클라우드 보안의 기본 어휘다.

## 실 사례(익명화) — DB를 인터넷에 안 열고 사설망에 둔 결정

> 실제 프로젝트 패턴을 익명화해 온다.

한 서비스에선 **DB(RDS)를 인터넷에 아예 안 열고 사설망(VPC) 안에** 뒀다 — 앱 서버(EC2)를 통해서만 접속 허용. 인터넷에 DB가 열려 있으면 매초 수천 건의 무차별 접속 시도를 받기 때문이다. 권한은 **최소 원칙(IAM)**으로 — 각 사용자/서비스는 필요한 최소 권한만, 루트 키는 안 쓰고 2단계 인증.

교훈: 보안의 목표는 "완벽히 막기"가 아니라 **"한 겹 뚫려도 다음 겹이 살린다"**는 층위 방어. DB를 사설망에(네트워크), 권한을 최소로(IAM), 비밀값은 환경변수로 — 이 셋이 겹쳐야 한 번의 뚫림이 전체로 번지지 않는다. 상담에서 "보안"을 물으면 이 세 단어(VPC·IAM·환경변수)가 기본 답이다.

## 흔한 실패 모드와 처방

- **DB를 인터넷에 연다.** 무차별 접속 시도 폭탄. 처방: RDS는 사설망에, 앱 서버에서만 접속.
- **권한을 '전체(Admin)'로 뿌린다.** 한 키 유출에 전 계정 털림. 처방: 최소 권한 원칙, 용도별 역할 분리.
- **루트 계정을 일상 쓴다 / 2FA 없다.** 계정 탈취 = 서비스 전체 탈취. 처방: 루트는 잠그고 2FA 필수.
- **비밀값을 코드에 박는다.** Git 유출 = 끝. 처방: 환경변수·Secret Manager.

## 상담에 바로 쓰는 한 줄

"보안"을 물으면, "DB는 사설망(VPC)에, 권한은 최소(IAM), 비밀값은 환경변수" 세 가지를 기본으로 말하라. 이게 클라우드 보안의 최소한이다.

## 개발자가 이 단어 말할 때

- **VPC / 서브넷** — 사설망 / 그 안의 구획(공개/비공개로 나눔).
- **보안그룹** — 자원 앞의 방화벽 규칙.
- **IAM / 역할(role) / 정책(policy)** — 권한 시스템 / 서비스용 권한 / 권한 규칙 문서.
- **루트 계정 / 2FA** — 전체 권한 계정 / 2단계 인증.
- **최소 권한 원칙** — 필요한 최소 권한만 주는 원칙.

## ✍️ 산출물 과제

본인 서비스의 자원(앱 서버, DB, 파일 저장)을 "인터넷에 열린 것 / 사설망에 가둘 것"으로 분류하라. 그리고 "이 자원에 접근하는 주체(사용자, 앱 서버, 관리자)마다 어느 권한까지 줄지"를 한 줄씩 적어보라(최소 권한 관점).

## 한 걸음 더 — 보안은 '파괴 반경(blast radius)'을 줄이는 일

보안을 완벽히 하는 건 불가능에 가깝다. 그래서 현실적 목표는 **"하나 뚫려도 전체가 무너지지 않게"** — 즉 침해의 파괴 반경(blast radius)을 줄이는 것이다. 이 개념이 VPC·IAM 설계의 밑바탕이다: DB를 사설망에 가두면(네트워크 격리) 한 서버가 털려도 DB가 바로 노출되지 않고, 권한을 최소화하면(IAM) 한 키가 유출돼도 그 키로 할 수 있는 일이 제한된다. 2단계 인증(2FA)도 같은 맥락 — 비밀번호가 뚫려도 두 번째 단계에서 막힌다. "왜 이렇게까지 복잡하게?"라는 질문에 답은 "한 겹이 뚫려도 다음 겹이 살린다"는 층위 방어다. 상담에서 보안을 말할 땐 "100% 막는 게 아니라, 뚫렸을 때 피해를 국소화한다"는 관점을 깔면 설득력이 다르다.
