개발자가 "이거 커밋하고 푸시하겠습니다"라고 할 때, 그 문장 안에는 "코드를 저장하고, 팀과 공유하고, 실제 서비스에 반영하는" 세 단계가 다 들어 있다. PM이 이 흐름을 모르면, "수정했는데 왜 사이트에 안 반영됐죠?"라는 질문을 자주 하게 된다. 답은 대개 "저장은 했지만 공유나 배포까지는 안 했기 때문"이다. 이 레슨은 Git과 GitHub가 각각 무엇이고, 거기서 코드가 어떻게 실제 서비스까지 흘러가는지를 다룬다.

## Git — 코드의 '저장'과 '이력'

Git은 **코드의 변경 이력을 저장하는 도구**다. 문서를 "최종", "최최종", "진짜최종"으로 복사해 두는 대신, 언제 무엇을 바꿨는지를 한 줄 한 줄 기록한다.

핵심 개념은 **커밋(commit)**이다. 커밋은 "이 시점의 코드 상태에 이름을 붙여 저장한다"는 행위다. 사진을 찍어 앨범에 넣는 것과 비슷하다. 언제든 특정 커밋으로 돌아갈 수 있고, 누가 언제 무엇을 바꿨는지도 알 수 있다. "어제는 됐는데 오늘 안 된다"면, 어제와 오늘 사이의 커밋을 비교해 원인을 좁힌다.

## 브랜치 — '동시에 여러 작업'을 가능하게 하는 것

**브랜치(branch)**는 같은 코드에서 여러 갈래로 동시에 작업하게 해주는 기능이다. 메인 줄기(main 브랜치)를 그대로 둔 채, "기능A 브랜치", "버그수정 브랜치"를 따로 만들어 작업한다. 그래서 한 사람이 새 기능을 만드는 동안 다른 사람이 버그를 고쳐도 서로 충돌하지 않는다.

작업이 끝나면 메인 줄기로 다시 합치는데, 이를 **머지(merge)** 또는 **풀 리퀘스트(pull request, PR)**라 부른다. PR은 "제가 이렇게 바꿨으니 검토하고 메인에 합쳐주세요"라는 요청이다. 회의에서 "PR 올렸습니다"는 "작업 끝냈으니 리뷰해 달라"는 뜻이다.

## GitHub — Git을 '공유'하는 곳

Git이 개인 컴퓨터 안에서 이력을 관리한다면, **GitHub**는 그 이력을 인터넷에 올려 팀과 공유하는 곳이다. GitHub = Git + 온라인 저장소.

- **푸시(push)**: 내 컴퓨터의 커밋을 GitHub로 올린다.
- **풀(pull)**: 남이 올린 변경을 내 컴퓨터로 내려받는다.

왜 굳이 GitHub가 필요한가. 내 컴퓨터가 고장 나면 코드가 사라지고, 팀원끼리 변경을 주고받기 어렵기 때문이다. GitHub가 "공식 원본(원격 저장소)" 역할을 해 모두가 같은 곳을 향해 작업한다. **"GitHub에 올렸다"는 "이제 팀 전체가 볼 수 있다"**는 뜻이다.

## 흐름 한 줄로: 작성 → 커밋 → 푸시 → 리뷰 → 배포

| 단계 | 이름 | 어디서 | 의미 |
|---|---|---|---|
| 1 | 코드 작성 | 내 PC | 기능을 만든다 |
| 2 | 커밋 | 내 PC (Git) | 한 시점을 저장한다 |
| 3 | 푸시 | 내 PC → GitHub | 팀과 공유한다 |
| 4 | PR/리뷰 | GitHub | 검토받고 메인에 합친다 |
| 5 | 배포 | GitHub → 서비스 | 실제 사이트에 반영한다 |

**PM이 꼭 알아야 할 구분은 3단계와 5단계다.** 푸시(3)는 "GitHub에 올렸다"지 "사용자가 보게 됐다"가 아니다. 사용자에게 보이려면 배포(5)까지 가야 한다. "수정했어요"라는 말이 어디까지를 가리키는지 — 커밋인가, 푸시인가, 배포인가 — 를 묻지 않으면 착각한다.

## 배포 — GitHub에서 실제 서비스로

**배포(deploy)**는 GitHub에 합쳐진 코드를 실제 서비스 환경으로 옮기는 일이다. 예전엔 개발자가 수동으로 파일을 올렸지만, 지금은 보통 **자동 배포**를 쓴다: GitHub의 메인 브랜치에 코드가 합쳐지면, Vercel·AWS 같은 클라우드가 알아서 그 코드를 가져가 사이트를 갈아끼운다.

- **프리뷰(미리보기) 배포**: 각 PR마다 임시 주소를 만들어 "이대로 합치면 이렇게 보입니다"를 보여준다. 리뷰·QA에 필수다.
- **프로덕션(실서버) 배포**: 메인에 합쳐진 코드가 실제 사용자가 쓰는 주소에 반영된다.

이 흐름을 **CI/CD**(지속적 통합/배포)라 부른다. 거창하지만, "코드 합치면 자동으로 검사하고 배포까지 해주는 파이프라인"이라고만 알면 된다.

한 가지 위험을 꼭 짚고 가자. Git/GitHub는 **비밀값(비밀번호, API 키, DB 접속 정보)을 올리는 곳이 아니다.** 한 번 푸시된 값은 이력에 영구히 남아, 저장소가 공개되거나 leaked되는 순간 치명적 사고가 된다. 그래서 비밀값은 `.gitignore`로 커밋 대상에서 빼고, 대신 **환경변수**(Phase 2에서 다룸)로만 다룬다. 개발자가 ".env는 커밋하지 않습니다"라고 강조하는 이유가 이것이다. 상담에서도 "비밀값은 코드에 직접 안 쓰죠?"를 기본 질문으로 달아 두면 보안 리스크를 한 번 줄인다.

## worked example: "로고만 바꿔 달라"는 요청의 여정

고객: "회사 로고만 새 걸로 바꿔주세요."

1. 개발자가 로고 파일을 바꾸고 **커밋**한다. → 아직 아무도 못 본다.
2. 브랜치를 만들어 **푸시**하고 PR을 연다. → 이제 팀은 볼 수 있다. 사용자는 못 본다.
3. PR에서 프리뷰 배포 주소로 확인한다. → 임시 주소에서 새 로고가 보인다. 실서버는 여전히 옛날 로고.
4. 리뷰 통과 후 메인에 **머지**. → 자동 배포가 돌아간다.
5. 1~2분 뒤 실제 사이트에 새 로고가 뜬다. → **이때서야 고객이 볼 수 있다.**

고객이 "바꿨나요?"라고 물을 때, 정답은 위 5단계 중 지금 몇 번인지로 대답한다. "PR 올렸습니다(3) → 5분 뒤 실서버 반영됩니다"라고 말하면 고객도 기다릴 수 있다.

## 흔한 실패 모드와 처방

- **"저장했는데 반영 안 됐다"고 착각.** 커밋은 했지만 푸시나 배포를 안 한 상태. 처방: "수정했습니다"라는 말 뒤에는 항상 "몇 단계까지 했는지"를 붙여 보고하라.
- **메인 브랜치에서 바로 작업.** 메인에서 직접 고치면 여러 사람의 변경이 엉키고, 실서버에 검증 안 된 코드가 들어갈 수 있다. 처방: 작업은 항상 브랜치를 따서 하고, PR로 검토받아 합친다.
- **배포 실패를 코드 버그로 오진.** 코드는 맞는데 환경변수·설정 문제로 배포가 터지는 경우가 흔하다(Phase 2·5 참고). 처방: "배포 로그"를 따로 보는 습관.

## 상담에 바로 쓰는 한 줄

"언제 고객이 볼 수 있나요?"를 물을 때, 개발자의 답이 "커밋/PR"에 머물러 있으면 실서버 반영까지의 시간을 따로 물어라. 둘은 다르다.

## 개발자가 이 단어 말할 때

- **"메인(main)"**: 실서버에 반영되는 공식 줄기.
- **"리베이스/머지 충돌"**: 같은 곳을 동시에 고쳐 합치기 어려운 상태. 작업 지연 신호.
- **"롤백"**: 문제 생겼을 때 이전 정상 커밋으로 되돌리는 일.
- **"CI 통과/실패"**: 자동 검사(테스트·빌드)가 잘 됐는지. 실패하면 배포가 멈춘다.

## ✍️ 산출물 과제

본인 팀의(또는 상상하는) 코드 수정이 "사용자에게 보이기까지" 거치는 단계를 커밋→푸시→PR→배포 순으로 한 줄씩 적어 보라. 각 단계에서 "이때 고객이 볼 수 있는가?"를 O/X로 표시하라. 정답은 마지막 배포 단계만 O여야 한다.
