에이전트 프레임워크 선택은 라이브러리 취향 문제로 보이지만 실제로는 **제어 모델의 선택**이다. 프레임워크마다 "에이전트의 다음 행동을 어떻게 표현하고 누가 통제하는가"의 철학이 다르고, 이 철학이 당신 코드의 디버깅 가능성·확장성·운영 안정성을 결정한다. 잘못 고르면 단순한 작업에 무거운 추상화를 짊어지거나, 복잡한 제어가 필요한데 평면적 루프에 흩뿌려 유지보수 불가능한 코드가 된다. 이 레슨은 smolagents·LangGraph·LlamaIndex의 제어 모델을 메커니즘 수준으로 비교하고 선택 기준을 세운다.

## 세 프레임워크의 철학과 제어 모델

**smolagents(Hugging Face)** 의 핵심은 최소주의와 **CodeAgent**다. 보통의 에이전트는 모델이 JSON 툴 호출(`{"tool": "search", "args": {...}}`)을 뱉으면 런타임이 파싱해 실행한다. CodeAgent는 이 대신 모델이 **실행 가능한 파이썬 코드 한 조각**을 생성해 행동한다. 행동이 곧 코드이므로 변수에 중간 결과를 담고, 반복·조건을 코드 자체로 표현하며, 여러 툴을 한 블록에서 조합할 수 있다. 장점은 투명성과 디버깅 — 에이전트가 "무엇을 했는가"가 사람이 읽는 코드로 남는다. 대가는 **코드 실행 샌드박스**가 필수라는 점이다. 모델이 생성한 코드를 그대로 실행하므로, 격리된 환경(예: 전용 실행기) 없이는 보안 사고로 직결된다.

**LangGraph** 는 에이전트를 **상태 그래프(state machine)** 로 모델링한다. 노드는 단계(LLM 호출, 툴 실행, 사람 검토 등), 엣지는 노드 간 전이, 공유 상태(state) 객체가 노드 사이를 흐른다. 순환(루프), 조건 분기, 휴먼인더루프(사람 승인 노드), 체크포인트(중간 상태 저장 후 재개)가 모두 **명시적**이다. 제어흐름이 코드 속에 암묵적으로 숨지 않고 그래프 구조로 드러난다. 복잡한 다단계·다분기 에이전트, 중단·재개가 필요한 프로덕션에 강하다. 대가는 학습 곡선과 보일러플레이트다.

**LlamaIndex** 는 **데이터/RAG 중심**이다. 인덱싱·검색·쿼리 엔진이 일급 시민이고, 에이전트는 그 검색 능력 위에 얹힌다. 지식 집약적 작업 — 대량 문서에 대한 질의응답, 검색이 작업의 본체인 경우 — 에 가장 자연스럽다. 강점은 데이터 파이프라인 통합이지 복잡한 제어흐름 표현이 아니다.

## Worked example: 같은 작업, 다른 제어 모델

"상위 3개 주문의 합계를 구하라"를 두 방식으로 비교한다(illustrative 의사코드).

**CodeAgent 방식** — 모델이 코드 한 조각을 생성하고 런타임이 샌드박스에서 실행한다.

```python
# 모델이 생성한 행동(코드). 런타임은 이 블록을 샌드박스에서 실행한다.
orders = get_orders(sort="amount", order="desc", limit=3)
total = sum(o["amount"] for o in orders)
final_answer(total)
```

한 번의 코드 생성 + 한 번의 실행으로 끝난다. 정렬·슬라이싱·합산이 코드 안에서 자연스럽게 합성된다.

**JSON 툴 다회 호출 방식** — 모델이 매 스텝 하나의 툴 호출만 제안하고, 결과를 관찰해 다음 호출을 만든다.

```text
LLM → call get_orders(sort="amount", limit=3)
런타임 → [{id:1, amount:90000}, {id:2, amount:70000}, {id:3, amount:50000}]
LLM → (관찰) 합산을 직접 할 수 없으니 ... 합을 추론하거나 add 툴 반복 호출
LLM → call add(a=90000, b=70000) → 160000
LLM → call add(a=160000, b=50000) → 210000
LLM → final_answer(210000)
```

스텝마다 LLM 왕복이 발생해 토큰·지연이 늘고, 모델이 산술을 직접 하려다 환각할 여지가 생긴다. CodeAgent는 이 합성 비용을 코드 실행으로 흡수한다 — 단, 그 대가가 샌드박스다.

## 선택 기준

한 줄 요약: **제어흐름이 그래프로 그려지고 분기·루프·재개 제어가 중요하면 LangGraph, 작업의 본체가 검색이면 LlamaIndex, 가볍고 투명한 코드 기반 행동을 원하면 smolagents.** 결정 순서를 권한다. (1) 이 에이전트의 상태 전이를 그래프로 그릴 수 있고 그 제어가 핵심인가 → LangGraph. (2) 작업의 80%가 인덱싱·검색·근거 제시인가 → LlamaIndex. (3) 둘 다 아니고 최소한의 추상화로 빠르게 만들고 싶은가 → smolagents. 세 프레임워크는 배타적이지 않다 — LangGraph 노드 안에서 LlamaIndex 검색을 호출하는 식의 조합이 흔하다.

### 흔한 실패 모드와 처방

**1. 유행 따라 무거운 프레임워크 선택.** 단일 툴을 한 번 부르면 끝나는 작업에 상태 그래프를 세우면, 코드의 90%가 작업이 아니라 프레임워크 시중이 된다. 처방: 제어흐름을 종이에 그려보고, 노드가 2~3개를 넘지 않으면 그래프 추상화를 버리고 평범한 함수로 짜라.

**2. 상태가 그래프인데 코드에 흩뿌린다.** 분기·재시도·재개가 필요한 에이전트를 평면적 while 루프와 플래그 변수로 구현하면, 전이 로직이 코드 곳곳에 숨어 추적 불가능해진다. 처방: 명시적 상태 머신(LangGraph)으로 전이를 한곳에 모아라.

**3. 코드 실행 샌드박스 누락.** CodeAgent류를 쓰면서 모델 생성 코드를 호스트에서 그대로 실행하면, 프롬프트 인젝션이 임의 코드 실행이 된다. 처방: 격리 실행기를 의무화하고, 네트워크·파일시스템 접근을 화이트리스트로 제한한다.

## 내 시스템에 연결하기

멀티 에이전트 Slack 시스템의 라우터+전문 에이전트+핸드오프 구조는 **LangGraph의 상태 그래프와 거의 일대일로 대응**한다 — 라우터 노드, 각 전문 에이전트 노드, 에이전트 간 핸드오프 엣지, 그리고 사람 승인이 필요한 지점의 휴먼인더루프 노드. 핸드오프 루프 폭주를 막는 정지 조건도 그래프의 조건 엣지(최대 핸드오프 횟수 초과 시 종료 노드로)로 명시할 수 있어, 제어가 코드에 숨지 않는다. Obsidian 메모리 스토어 기반 RAG는 **LlamaIndex의 인덱싱·쿼리 엔진**으로 감싸 각 에이전트의 검색 툴로 노출하기 좋다 — 노트 컬렉션을 인덱스로 만들고, 에이전트는 그 위의 query 툴만 부른다. 전문 에이전트 내부의 다단계 데이터 가공(여러 노트 교차 합산 등)은 smolagents의 CodeAgent로 두면 합성 비용을 코드로 흡수하되, 반드시 샌드박스 안에서 돌려야 한다.

## ✍️ 산출물 과제

당신 시스템에 들일 에이전트 하나를 골라, **어느 프레임워크의 제어 모델이 맞는지**를 한 문단으로 정당화하라. 다음 용어를 명시할 것: **제어 모델**, **상태 그래프(노드·엣지·전이)**, **CodeAgent와 JSON 툴 호출의 차이**, **코드 실행 샌드박스**. "상태 전이를 그래프로 그릴 수 있는가 / 작업의 본체가 검색인가"를 판별 근거로 삼고, 선택한 프레임워크가 강제하는 운영 요구사항(예: 샌드박스, 체크포인트 저장소)을 한 문장으로 적어라.
