프롬프트는 모델에게 보내는 "주문서"가 아니다. 그것은 모델이 가진 거대한 출력 분포를, 당신이 원하는 영역으로 좁혀 들어가는 **인터페이스 설계**다. 동일한 질문이라도 프롬프트의 구조에 따라 모델은 신뢰할 만한 한 줄을 내놓기도 하고, 매번 형식이 흔들리는 자유서술을 토해내기도 한다. 이미 RAG와 멀티 에이전트를 운영 중이라면 이 차이가 곧 파이프라인의 안정성이다. 파싱이 깨지면 다운스트림 전체가 멈추기 때문이다. 이 레슨은 "잘 부탁하는 법"이 아니라, 출력 분포를 통제하는 메커니즘을 다룬다.

## System과 User 프롬프트: 역할의 분리

System 프롬프트는 **지속적 맥락**이다. 모델이 누구이고, 어떤 제약 아래 동작하며, 무엇을 절대 하지 말아야 하는지 같은 — 대화 내내 변하지 않는 헌법을 담는다. User 프롬프트는 **그때그때의 요청**이다. 이번 턴에 처리할 구체적 입력이 들어간다.

이 둘을 섞으면 제약이 흐려진다. 예를 들어 "너는 신중한 분석가다. 모르면 모른다고 답하라"라는 영구 규칙을 매 User 메시지에 끼워 넣으면, 모델은 그 규칙을 영구 정책이 아니라 이번 요청의 일부로 해석한다. 사용자가 다음 턴에 다른 톤으로 요청하면 규칙은 묻혀버린다. 더 위험한 것은 신뢰 경계가 무너지는 것이다. System은 당신(개발자)이 통제하는 신뢰된 영역이고, User는 외부 입력이 들어오는 영역이다. 제약을 User에 두면, 외부 입력이 같은 평면에서 그 제약을 덮어쓸 수 있다(이는 다음 레슨의 인젝션 주제와 직결된다). 규칙은 System에, 데이터는 User에 — 이 분리가 통제의 출발점이다.

## 핵심 기법 네 가지, 메커니즘까지

**① Few-shot — in-context learning.** 모델은 추가 학습 없이, 프롬프트 안에 주어진 입력-출력 쌍의 패턴을 그 자리에서 모방한다. 예시 2~3개가 형식과 톤을 고정하는 이유는, 모델이 "다음 토큰"을 예측할 때 직전 예시들이 강력한 조건이 되기 때문이다. 예시가 "이 작업의 출력은 이렇게 생겼다"는 분포를 좁혀준다. 핵심은 예시가 **당신이 원하는 출력과 동일한 형식**이어야 한다는 점이다. 예시의 라벨이 한쪽으로 치우치거나 형식이 제각각이면, 그 편향과 산만함을 그대로 학습한다.

**② Chain-of-thought(CoT) — 추론 토큰을 먼저 생성.** 모델은 토큰을 하나씩 순차 생성하며, 각 토큰을 만들 때 그 앞의 모든 토큰을 조건으로 쓴다. 답을 곧장 내라고 하면 모델은 한 번의 forward pass 안에서 모든 추론을 압축해야 한다. 반면 "단계별로 생각하라"고 하면, 모델은 중간 추론을 **실제 토큰으로 풀어 쓰고**, 그 토큰들을 다시 조건으로 삼아 최종 답을 낸다. 즉 추론에 쓸 연산 자체가 늘어난다. 대가는 분명하다. 추론 토큰만큼 지연과 비용이 증가한다. 그래서 CoT는 복잡한 추론이 필요한 호출에만 켜야 한다.

**③ Structured output — 형식 강제.** 출력을 JSON이나 명시적 태그로 강제하면, 후속 코드가 결과를 안정적으로 파싱할 수 있고, 코드 기반 평가(필드 존재 여부, 타입 검사)가 가능해진다. 강력한 보조 수단이 **prefill**이다. 모델의 응답 첫머리를 `{` 같은 토큰으로 미리 채워 시작하면, 모델은 그 형식을 이어갈 수밖에 없어 산문 서두("물론입니다, 여기...")가 끼어들 여지가 사라진다.

**④ 역할과 제약 명시.** 역할("너는 보수적인 회계 검토자다")은 모델이 끌어올 분포를 좁히고, 제약은 가드레일을 세운다. 특히 "확실하지 않으면 '모름'이라고 답하라"는 한 줄은, 모델이 빈칸을 그럴듯한 추측으로 메우려는 경향(환각)을 눈에 띄게 줄인다. 모름을 허용된 출력으로 명시했기 때문이다.

## Worked example: 같은 요청, 다른 설계 (illustrative)

요청: "이 분기 매출 보고를 요약하라."

나쁜 프롬프트:
```
다음 보고서를 요약해줘:
{report_text}
```
문제: 길이도, 형식도, 의견 허용 여부도 정해지지 않았다. 출력은 매 호출마다 다섯 문장이었다가 한 문단이었다가, 없는 숫자를 반올림하거나 "전망이 밝다" 같은 의견을 끼워 넣는다. 다운스트림 코드가 이를 파싱하려면 매번 깨진다.

좋은 프롬프트(System에 규칙, User에 데이터, structured 출력):
```
System: 너는 사실만 다루는 재무 요약기다.
규칙: (1) 3문장 이내. (2) 원문의 숫자는 변형 없이 보존.
(3) 의견·전망·추측 금지. (4) 확신 없는 항목은 생략.
출력은 아래 JSON 스키마만 반환:
{"summary": string, "figures": [string]}

User: {report_text}
```
왜 후자가 안정적인가. 형식(JSON), 길이(3문장), 사실성(숫자 보존·의견 금지), 환각 억제(확신 없으면 생략)를 각각 별개의 제약으로 못 박았기 때문이다. 출력 분포가 좁아져 호출 간 분산이 줄고, `figures` 필드를 코드로 검증할 수 있다. 핵심 원칙은 **명확성 > 영리함**이다. 모델을 교묘하게 구슬리는 트릭보다, 원하는 것을 모호함 없이 명시하는 편이 거의 항상 더 견고하다.

## 트레이드오프와 흔한 실패 모드

- **System/User 혼용.** 영구 규칙을 User에 넣어 제약이 한 턴짜리로 전락. → 처방: 규칙은 System, 입력 데이터는 User로 일관 분리.
- **CoT 남발.** 단순 분류·추출까지 CoT를 켜서 토큰·지연·비용이 폭증. → 처방: 추론 난도로 게이팅. 단순 작업은 직답+structured, 복잡 추론만 CoT.
- **자유서술 수용.** 형식을 강제하지 않아 파싱이 깨지고 다운스트림이 멈춤. → 처방: JSON 스키마 강제 + prefill로 서두 차단 + 코드 단에서 스키마 검증 후 실패 시 재시도.

## 내 시스템에 연결하기

- **멀티 에이전트 Slack 시스템.** 라우터와 각 전문 에이전트의 페르소나·핸드오프 규칙은 **System 프롬프트**에 고정하라. 사용자 메시지(User)에 절대 넣지 말 것 — 그래야 외부 입력이 라우팅 정책을 흔들지 못한다. 에이전트 간 핸드오프 페이로드는 자유서술이 아니라 **JSON 스키마**(다음 에이전트, 위임 사유, 컨텍스트 요약)로 고정해, 받는 쪽이 코드로 파싱하게 하라. 라우팅 분류는 단순 작업이니 CoT를 끄고 직답시키되, 실제 도메인 추론을 하는 에이전트에서만 CoT를 켜 비용을 관리한다.
- **Obsidian 메모리 스토어(노트 RAG).** 검색된 노트를 요약·추출할 때, 위 worked example의 "사실 요약기" 패턴을 그대로 적용하라. "원문 숫자 보존, 의견 금지, 확신 없으면 생략"을 System에 두고 노트 본문을 User로 넘긴다. few-shot 예시 2~3개로 출력 노트 형식을 고정하면, 메모리에 다시 저장되는 노트의 형식이 통일된다.
- **Blob 커맨드 큐.** 큐에 적재되는 커맨드는 LLM이 자연어를 JSON으로 변환해 만든다. 이 변환 호출에 structured output + prefill을 강제하고, 워커가 꺼내 실행하기 전 **스키마 검증 게이트**를 두라. 검증 실패 시 실행하지 말고 재생성 큐로 돌린다.

## ✍️ 산출물 과제

당신의 시스템에서 출력이 가장 자주 깨지는 LLM 호출 하나를 골라, 다음 용어를 정확히 써서 한 문단으로 재설계하라: **출력 분포(좁히기)**, **System/User 분리**, **few-shot(in-context learning)**, **chain-of-thought(추론 토큰)**, **structured output**, **prefill**, **스키마 검증 게이트**. 어떤 제약을 System에 두고, 어떤 형식을 강제하며, CoT를 켤지 끌지, 그 판단 기준을 함께 적을 것.
