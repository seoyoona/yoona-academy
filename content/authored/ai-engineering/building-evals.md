프롬프트 한 줄을 고치고 배포했더니 라우터 정확도가 조용히 3% 떨어졌다 — 그런데 아무도 몰랐다. 평가 하니스가 없었기 때문이다. eval set이 코드처럼 버전 관리되고 CI에서 자동으로 돌아가지 않으면, 모든 프롬프트·모델 변경은 도박이 된다. 좋아졌는지 나빠졌는지를 매번 손으로 몇 케이스 돌려보며 "느낌상 괜찮네"로 판단하게 되고, 그 느낌은 회귀를 놓친다. 평가 하니스를 직접 만드는 일은 선택이 아니라, LLM 시스템을 운영하는 사람의 기본기다.

## 하니스의 세 부품: 데이터셋 · 채점기 · 러너

평가 하니스는 세 부품으로 분해된다. **데이터셋**은 입력과 (있다면) 기대 출력의 모음, **채점기(grader)**는 실제 출력을 받아 통과/점수를 내는 함수, **러너**는 데이터셋의 각 케이스에 시스템을 돌리고 채점기를 호출해 결과를 집계하는 루프다. 이 셋이 분리되어 있어야 — 데이터셋은 늘리고, 채점기는 교체하고, 러너는 CI에 꽂는 식으로 — 각각을 독립적으로 진화시킬 수 있다.

**데이터셋**의 품질이 평가 전체의 천장을 정한다. 합성 데이터(LLM이 만든 가상 케이스)는 부트스트랩엔 쓸 만하지만, 진짜 어려운 케이스는 **실제 트래픽**에 있다. 사용자가 실제로 보낸 애매한 문의, 시스템이 틀렸던 입력 — 이런 것이 골든셋의 핵심이다. 골든셋 부트스트랩 절차는 대략 이렇다: (1) 프로덕션 로그에서 다양한 케이스를 표집한다, (2) 두 명 이상이 독립적으로 정답을 라벨링한다, (3) 둘의 라벨이 얼마나 일치하는지 — **inter-annotator agreement(평가자 간 일치도)** — 를 측정한다. 일치도가 낮으면 "정답"이 모호하다는 뜻이고, 이건 채점기 탓이 아니라 **작업 정의 자체가 흐릿하다**는 신호다. 이 경우 기준(rubric)을 다듬어 사람끼리 먼저 합의를 맞춘 뒤에야 모델 채점을 논할 수 있다.

## 채점기 3종, 그리고 "코드로 최대한 떨어뜨려라"

채점기는 세 종류로 갈린다.

- **코드 기반:** 정규식, JSON 스키마 검증, exact match 같은 결정적 함수. 싸고, 빠르고, **100% 재현 가능**하다.
- **모델 기반(LLM-judge):** 코드로 못 재는 품질(자연스러움, 도움됨)을 강한 모델에게 채점시킨다. 유연하지만 비싸고 흔들린다.
- **사람:** 가장 정확하지만 가장 비싸고 느리다. 최종 검증과 골든셋 라벨링에 아껴 쓴다.

핵심 원칙은 **가능한 한 많은 케이스를 코드 기반 채점기로 떨어뜨려라**다. 출력이 구조화되어 있거나(JSON, enum, 숫자), 정답이 명확히 정의되면 judge를 쓸 이유가 없다 — judge는 더 비싸고 덜 재현적이다. judge는 코드로 도저히 못 잡는 "주관적 품질"에만 아껴 쓴다. 이 우선순위를 지키면 평가 비용은 내려가고 신뢰성은 올라간다.

worked example. 라우터가 `{"agent": "billing"}` 형태의 JSON을 내야 하고, 정답 라벨이 있는 케이스를 채점한다고 하자. judge에게 "이 라우팅이 맞나요?"를 물어볼 이유가 전혀 없다. 코드 기반 grader 한 함수면 끝난다:

```python
import json

VALID = {"billing", "support", "sales", "tech", "general"}

def grade_router(raw_output: str, expected: str) -> dict:
    try:
        obj = json.loads(raw_output)          # 파싱 실패 = 오답
    except json.JSONDecodeError:
        return {"pass": False, "reason": "invalid_json"}
    agent = obj.get("agent")
    if agent not in VALID:                     # 스키마 위반 = 오답
        return {"pass": False, "reason": "unknown_agent"}
    return {"pass": agent == expected,
            "reason": "match" if agent == expected else "wrong_agent"}
```

이 grader는 호출당 비용이 0이고, 같은 입력에 항상 같은 판정을 내며(100% 재현), 실패 이유를 `invalid_json` / `unknown_agent` / `wrong_agent`로 분류까지 해준다. 같은 일을 judge로 하면 호출 비용이 붙고, 같은 입력에 다른 판정이 나올 수 있으며, "왜 틀렸나"를 다시 파싱해야 한다. 라우터처럼 정답이 명확한 작업에서 judge를 쓰는 건 돈과 신뢰성을 둘 다 버리는 일이다.

## 평가의 CI화와 살아있는 eval set

하니스의 진짜 가치는 **반복**에서 나온다. 프롬프트를 고치거나 모델을 바꿀 때마다 **같은** eval set으로 회귀를 측정해야 한다. 이걸 CI에 꽂으면 — PR마다 러너가 돌아 통과율을 출력하고, 임계값 아래로 떨어지면 머지를 막는 — 조용한 회귀가 배포 전에 잡힌다. 변경 전후 통과율을 나란히 찍어주는 것만으로도 "이 변경이 정말 개선인가"라는 질문에 데이터로 답할 수 있다.

그리고 eval set은 **살아있는 자산**이어야 한다. 프로덕션에서 시스템이 틀린 케이스가 나올 때마다 그 입력과 정답을 eval set에 추가한다. 그러면 한 번 겪은 실패는 다시는 같은 방식으로 통과하지 못하고(회귀 방지), eval set은 시스템이 실제로 부딪히는 현실을 점점 더 잘 반영하게 된다. 처음 50개로 시작한 셋이 6개월 뒤 500개가 되어 있다면, 그건 건강한 시스템의 징후다.

## 트레이드오프와 실패 모드

채점기 선택 기준: **정답이 코드로 검증 가능하면 코드 기반, 주관적 품질이면 judge, 최종 신뢰성 검증과 라벨링이면 사람.** 항상 코드 기반을 먼저 시도하고, 안 될 때만 위로 올라간다.

실패 모드 셋. 첫째, **합성 데이터만으로 평가** — LLM이 만든 깔끔한 케이스만 보면 통과율이 높게 나오지만, 실제 트래픽의 지저분한 입력에서 무너진다. 처방: 골든셋의 중심을 프로덕션 로그에서 표집한 까다로운 케이스로 채운다. 둘째, **모든 걸 judge로** — 코드로 충분한 구조화 출력까지 judge에 맡겨 비용이 치솟고 판정이 흔들린다. 처방: judge 사용 전에 "이건 코드로 못 잡나?"를 먼저 묻는다. 셋째, **eval set 정체** — 한 번 만들고 안 늘리면, 시스템은 그 고정된 셋에만 과적합되고 새 실패 유형을 영영 못 잡는다. 처방: 프로덕션 실패를 eval set에 더하는 절차를 운영 루틴에 박아 넣는다.

## 내 시스템에 연결하기

**멀티 에이전트 Slack 시스템**의 라우터에는 위 worked example의 코드 기반 grader를 그대로 적용한다 — 출력이 `{"agent": ...}` enum이므로 judge가 필요 없다. 데이터셋은 실제 Slack 메시지에서 표집한 까다로운 사례(여러 에이전트에 걸치는 모호한 문의)로 채우고, 라우터가 프로덕션에서 틀린 메시지는 정답 라벨과 함께 즉시 eval set에 추가한다. 러너는 CI에 꽂아 프롬프트 변경 PR마다 라우팅 통과율을 출력하게 한다. 핸드오프 메시지의 자연스러움처럼 코드로 못 재는 품질만 pairwise judge로 따로 평가한다.

**Obsidian 메모리 스토어** RAG는 두 층으로 채점한다: 검색 단계는 "정답 노트가 top-k에 들어왔나"를 코드 기반(노트 ID 매칭)으로, 생성 단계는 faithfulness를 judge로. 검색이 실패한 질의는 골든셋에 추가해 임베딩·청킹 변경 시 회귀를 막는다.

**Blob 커맨드 큐**의 LLM 파싱 단계는 출력 스키마가 정해져 있으므로 전적으로 코드 기반 grader(JSON 스키마 검증)로 채점한다. 워커가 파싱에 실패하거나 잘못 분류한 커맨드는 데드레터에서 회수해 eval set에 넣어, 큐 처리 로직을 바꿀 때마다 같은 셋으로 회귀를 측정한다.

## ✍️ 산출물 과제

당신 시스템의 한 작업에 대한 평가 하니스를 정확한 용어로 한 문단 설계하라. 반드시 다음 용어를 사용할 것: **데이터셋 · 채점기(grader) · 러너**, **코드 기반 / 모델 기반(LLM-judge) / 사람**, **inter-annotator agreement(평가자 간 일치도)**, **eval set의 CI화**, **살아있는 자산**. 어느 채점기를 왜 골랐는지(코드로 떨어뜨릴 수 있는가), 골든셋을 어디서 부트스트랩할지, 프로덕션 실패를 어떻게 eval set에 환류할지를 명시하라.
