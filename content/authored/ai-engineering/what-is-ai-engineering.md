당신이 RAG 파이프라인을 운영하고, 여러 에이전트를 라우터로 묶고, 커맨드를 큐에 적재해 워커로 처리하고 있다면, 이미 "AI 엔지니어링"을 실천하고 있는 것이다. 그러나 이 분야가 ML 엔지니어링과 무엇이 본질적으로 다른지를 정확히 구분하지 못하면, 잘못된 곳에 시간을 쏟게 된다. 예를 들어 분류 정확도가 낮을 때 ML 엔지니어의 반사신경은 "데이터를 더 모아 재학습"이지만, AI 엔지니어의 레버는 "프롬프트·few-shot·평가셋"이다. 같은 증상에 처방이 다르다. 이 차이를 못 짚으면, 가중치를 건드릴 수 없는 상황에서 가중치를 건드리려는 헛수고를 하거나, 반대로 프롬프트 한 줄로 풀릴 문제에 파인튜닝 파이프라인을 세운다. 이 레슨은 그 경계선을 정확한 용어로 긋는다.

## 모델은 상수, 그 주변이 변수다

ML 엔지니어링은 **모델 자체를 만드는 일**이다. 데이터를 모으고, 라벨을 붙이고, 손실함수를 정의하고, 경사하강으로 가중치를 갱신하고, 검증셋으로 일반화를 확인한다. 산출물은 학습된 가중치다.

AI 엔지니어링은 **이미 학습된 foundation model 위에 애플리케이션을 짓는 일**이다. 모델의 가중치는 당신이 건드릴 수 없는 상수다. 당신이 통제하는 변수는 모델 바깥에 있다.

- **프롬프트**: 모델에 들어가는 지시·역할·제약·출력 형식.
- **검색(retrieval)**: 어떤 외부 컨텍스트를 어떻게 찾아 프롬프트에 주입할지.
- **툴**: 모델이 호출할 수 있는 함수·API·코드 실행.
- **평가(eval)**: 출력이 "맞는지"를 판정하는 셋과 기준.
- **오케스트레이션**: 여러 호출·에이전트·재시도·분기를 어떻게 엮을지.

핵심 통찰은 이것이다. ML 엔지니어가 "모델을 좋게 만들어" 문제를 풀던 자리에, AI 엔지니어는 "모델은 고정한 채 그 입력·출력·연결을 설계해" 문제를 푼다. 가중치라는 거대한 자유도가 사라지는 대신, 프롬프트·컨텍스트·오케스트레이션이라는 새로운 설계 표면이 열린다.

이 분야가 별도로 생긴 이유는 foundation model의 등장으로 **"모델을 만드는 사람"과 "모델로 제품을 만드는 사람"이 분리**되었기 때문이다. 과거에는 분류기 하나를 쓰려면 직접 학습해야 했으니, 데이터·GPU·ML 전문성이 진입장벽이었다. 지금은 범용 모델이 API 뒤에 있으니, 진입장벽이 "학습 역량"에서 "주변 시스템 설계 역량"으로 옮겨갔다. 비용 구조도 바뀐다. 선행 학습 비용(데이터 수집·GPU 학습)이 사라지는 대신, **추론 비용**(호출당 토큰 과금·지연·처리량)이 운영의 핵심 변수로 올라온다.

## 일의 내용이 어떻게 옮겨가는가

ML 엔지니어링의 작업들이 사라지는 게 아니라, 인접한 다른 작업으로 **대응 이동**한다. 같은 목표(좋은 시스템)를 향하지만, 레버가 바뀐다.

| ML 엔지니어링 | AI 엔지니어링 | 공통 목표 |
|---|---|---|
| 데이터 수집·라벨링 | 평가셋 설계 (대표 입력 + 기대 출력) | 무엇이 "맞음"인지 정의 |
| 손실함수·하이퍼파라미터 튜닝 | 프롬프트·컨텍스트 설계 | 출력 품질을 끌어올림 |
| 모델 아키텍처 선택 | 모델 선택 + 오케스트레이션 설계 | 시스템 구조 결정 |
| 모델 배포·서빙 | 추론 비용·지연·idempotency 운영 | 안정적 프로덕션 운영 |
| 학습/검증 분리 | 평가셋/회귀 테스트 분리 | 변경이 회귀를 일으키지 않게 보장 |

특히 마지막에 주목하라. ML에서 라벨링이 모델 품질의 상한을 정했듯, AI 엔지니어링에서는 **평가셋이 시스템 개선의 상한**을 정한다. 평가가 없으면 프롬프트를 바꿔도 좋아졌는지 알 수 없다. 그리고 idempotency 같은 분산 시스템 관심사가 새로 들어온다. 동일 요청이 재시도로 두 번 실행되면 부수효과(예: 결제·메시지 발송)가 중복될 수 있기 때문이다.

## worked example: "고객 문의 분류"를 두 방식으로

요구사항: 들어온 고객 문의를 `결제 / 배송 / 환불 / 기타` 4범주로 분류한다.

**ML 엔지니어의 접근**

1. 과거 문의 수천~수만 건을 모은다.
2. 사람이 각 건에 4범주 라벨을 붙인다(라벨링 비용·기간이 든다).
3. 텍스트를 임베딩하거나 TF-IDF로 벡터화하고, 로지스틱 회귀나 작은 트랜스포머 분류기를 학습한다.
4. 검증셋으로 정확도·F1을 측정하고 하이퍼파라미터를 조정한다.
5. 모델을 서빙하고, 분포가 바뀌면(신규 범주 등장) 데이터를 다시 모아 재학습한다.

상한은 라벨 데이터의 양과 질이 정한다. 신규 범주 추가는 곧 재라벨링·재학습이다.

**AI 엔지니어의 접근**

1. 프롬프트를 쓴다. 예를 들어:

```text
다음 고객 문의를 [결제, 배송, 환불, 기타] 중 하나로 분류하라.
JSON으로만 답하라: {"category": "..."}

예시:
문의: "카드가 두 번 결제됐어요" -> {"category": "결제"}
문의: "주문한 게 일주일째 안 와요" -> {"category": "배송"}
문의: "받은 물건이 마음에 안 들어요" -> {"category": "환불"}

문의: "{{message}}"
```

2. 대표 문의 50~100건에 정답을 달아 **평가셋**을 만든다(라벨링이 아니라 평가용 소량).
3. 평가셋으로 정확도를 측정한다. 예를 들어 87%가 나오면, 오답을 분석해 few-shot 예시를 보강하거나 출력 형식을 조인다.
4. 신규 범주가 필요하면 프롬프트의 범주 목록과 예시 한두 개만 고친다. 재학습이 없다.

대비가 분명하다. ML 쪽은 **데이터의 양**이 자산이자 병목이고, AI 쪽은 **프롬프트·few-shot·평가셋**이 레버다. 라벨링은 "학습용 수만 건"에서 "평가용 수십~수백 건"으로 줄고, 반복 주기는 "재학습 며칠"에서 "프롬프트 수정 수 분"으로 짧아진다. 대신 AI 쪽은 호출당 토큰 비용·지연을 매 요청 떠안는다.

## 언제 ML로, 언제 AI 엔지니어링으로

- **초기·소량·빠른 반복**이 필요하면 AI 엔지니어링부터. 라벨 데이터가 없거나 요구가 자주 바뀌는 상황에서 프롬프트는 즉시 고칠 수 있다.
- **초대량·초저지연·초저비용**이 지배적 제약이면 전용 모델 학습(ML)이 유리할 수 있다. 예를 들어 초당 수만 건을 밀리초 단위로 분류해야 하면, 작은 전용 분류기가 LLM 호출보다 싸고 빠르다.
- **풍부한 자체 라벨 데이터**가 이미 있고 과제가 안정적이라면 ML 학습의 상한이 더 높을 수 있다.
- 현실에서는 **혼합**이 흔하다. LLM으로 초기 라벨을 싸게 생성해 작은 분류기를 학습시키는 식의 증류(distillation)가 한 예다.

## 흔한 실패 모드와 처방

- **레버를 헷갈린다.** 출력이 나쁠 때 "모델이 약하다"며 모델을 바꾸지만, 사실은 프롬프트·컨텍스트가 부실한 경우가 많다. 처방: 모델 교체 전에 프롬프트와 검색 품질부터 평가셋으로 검증하라. 통제 가능한 변수(프롬프트·retrieval)를 먼저 소진하라.
- **평가 없이 손본다.** 평가셋 없이 프롬프트를 고치면 "좋아진 느낌"만 남고 회귀를 못 잡는다. 처방: 첫 주에 작은 평가셋부터 만들어라. 모든 변경은 그 셋을 통과해야 한다.
- **추론 운영을 ML 사고로 본다.** 학습 비용은 0이지만 추론 비용·지연·재시도 중복이 운영을 망친다. 처방: 호출당 토큰·지연을 메트릭으로 잡고, 부수효과 있는 작업엔 idempotency 키를 둬라.

## 내 시스템에 연결하기

당신의 **멀티 에이전트 Slack 시스템**에서 라우터는 "어떤 메시지를 어느 전문 에이전트로 보낼지" 분류하는 컴포넌트다. 이것이 바로 위 worked example의 "문의 분류"와 동형이다. 라우팅이 틀릴 때 반사적으로 "더 센 모델"을 떠올리지 말고, 먼저 라우터 프롬프트와 라우팅 평가셋(대표 메시지 + 기대 에이전트)을 점검하라. 통제 변수는 프롬프트·few-shot이지 가중치가 아니다.

**Obsidian 메모리 스토어**의 의미 검색은 AI 엔지니어가 통제하는 *retrieval* 레버 그 자체다. 답변이 부실할 때 모델 탓을 하기 전에 "올바른 노트가 검색되어 컨텍스트로 들어갔는가"를 먼저 확인하라. 검색이 빗나가면 어떤 모델도 못 구한다.

**Blob 커맨드 큐**는 AI 엔지니어링 고유의 *추론 운영* 관심사가 사는 곳이다. 워커가 비동기로 처리하다 재시도하면 같은 커맨드가 두 번 실행될 수 있으니, 커맨드에 idempotency 키를 부여해 부수효과 중복을 막아라. 이것은 ML 학습 파이프라인엔 없던, 오직 추론 운영에서만 생기는 문제다.

## 이 트랙의 지도

- **평가**: "좋아졌는지"를 측정 가능하게 만든다 — 모든 개선의 전제.
- **프롬프트**: 모델 입력을 설계해 품질을 끌어올린다 — 가장 싸고 빠른 레버.
- **RAG**: 외부 지식을 검색해 컨텍스트로 주입한다 — 모델이 모르는 것을 알게 한다.
- **에이전트**: 툴 사용·다단계 추론·핸드오프로 복잡한 작업을 자동화한다.
- **운영**: 비용·지연·idempotency·관측을 다뤄 프로덕션을 안정화한다.

## ✍️ 산출물 과제

당신이 운영 중인 시스템 하나를 골라, "이것이 ML 엔지니어링이 아니라 AI 엔지니어링인 이유"를 한 문단으로 정확한 용어로 설명하라. 반드시 다음 용어를 명시적으로 사용하라: **foundation model(상수로서의 모델)**, **통제 변수(프롬프트·retrieval·툴·평가·오케스트레이션)**, **평가셋**, **추론 비용·idempotency**. "모델을 학습한다"가 아니라 "고정된 모델 주변을 설계한다"는 구도가 드러나야 한다.
